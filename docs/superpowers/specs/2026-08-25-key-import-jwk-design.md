**Date**: 2026-08-25
**Status**: Proposed
**Scope**: `internal/crypto/provider.go`, `internal/crypto/software_provider.go`,
`internal/crypto/pkcs11_provider.go`, `internal/signing/jwk_parse.go` (new),
`internal/services/keys/key_service.go`, `internal/services/retry/retry_key_service.go`,
`internal/services/keys/mocks/mock_KeyService.go` (generated),
`internal/services/authorization/data_actions.go`, `api/keys.go`,

**Branch target**: v-4.0.0
**Source finding**: `.claude/azure-keyvault-parity.md` §2, "Import key" row

`.claude/roadmap-azure-parity-and-beyond.md` (line 39, "Key import (JWK)")

See also: [2026-08-25-key-export-decision-record.md](2026-08-25-key-export-decision-record.md)
resolves the opposite question — this doc is import only, and its Design §1
deliberately re-establishes the same non-extractability guarantee for imported
HSM keys that the decision record commits to for generated ones.

---

## Problem

Azure Key Vault lets you import existing key material via `POST /keys/{name}/import`
(JWK), not just generate new keys. RocketVault has no import endpoint at all —
and the gap is not merely unbuilt, it's unroutable even in the authorization layer:

- `model/azure_roles.go:51-54` declares the action:
  ```go
  // ActionKeysImport permits importing externally generated key material.
  // No HTTP route maps to it yet; it exists so the Crypto Officer and
  // Administrator bundles match Azure exactly.
  ActionKeysImport DataAction = "Microsoft.KeyVault/vaults/keys/import/action"
  ```
- It's already granted to `RoleKeyVaultAdministrator` (`model/azure_roles.go:161`)
  and `RoleKeyVaultCryptoOfficer` (`model/azure_roles.go:192`).
- But `mapKeyAction` (`internal/services/authorization/data_actions.go:140-208`),
  the single dispatch function that maps every key route to a `DataAction`, has no
  `case "import"` anywhere — so no HTTP path, existing or hypothetical, can ever
  produce `ActionKeysImport` today. The role grants are inert.

This is a real, already-tracked adoption blocker: `.claude/azure-keyvault-parity.md:40`
puts it plainly — *"no import route ... but no path maps to it"* — and the roadmap
doc frames the impact: *"Real gap for anyone migrating existing keys in from another
system rather than starting fresh — a common enterprise need and a real adoption
blocker without it"* (`.claude/roadmap-azure-parity-and-beyond.md:39-43`).

## Goals

- `POST /keys/import` (and its vault-scoped equivalent) accepts a caller-supplied
  JWK and stores it exactly as if it had been generated by RocketVault — same
  encryption, same PKCS#11-vs-software branching, same downstream operations
  (sign/verify/encrypt/decrypt/wrap/unwrap all work on an imported key
  identically to a generated one).
- `rocketvault keys import` CLI command, mirroring `keys create`'s authorization
  and output pattern.
- An imported key on an HSM-backed vault ends up exactly as non-extractable as a
  generated one — import must not become a backdoor around the guarantee
  [2026-08-25-key-export-decision-record.md](2026-08-25-key-export-decision-record.md)
  just committed to.

## Non-goals

- No support for Azure's HSM-protected "release policy" import flow (wrapped key
  blobs with an attestation-gated release policy). v1 is plaintext-JWK import
  only — the caller supplies raw key material over the (already TLS-protected)
  API, same trust model as every other write in this API.
- No change to `GetKey`/`GetPublicJWK`/`ListKeys` response shapes. An imported key
  is indistinguishable from a generated one in every read path.
- No new symmetric (OCT) key import in this pass — OCT keys are HSM-only by
  existing policy (`crypto.ErrOctKeysRequireHSM`), and generalizing import across
  all three key families at once is unnecessary scope; RSA and ECDSA cover the
  BYOK migration case the roadmap doc cites. OCT import can follow the identical
  pattern later as a small extension, not a redesign.

## Design

### 1. `crypto.KeyProvider` interface — add `ImportKey`

The interface (`internal/crypto/provider.go:10-41`) currently has only generation
and use operations:

```go
type KeyProvider interface {
	GenerateRSAKey(ctx context.Context, bits int) (handle string, err error)
	GenerateECDSAKey(ctx context.Context, curveName string) (handle string, err error)
	GenerateAESKey(ctx context.Context, bits int) (handle string, err error)
	Sign(ctx context.Context, handle string, keyType string, data []byte, algorithm SignatureAlgorithm) ([]byte, error)
	Verify(ctx context.Context, handle string, keyType string, data []byte, sig []byte, algorithm SignatureAlgorithm) (bool, error)
	Encrypt(ctx context.Context, handle string, data []byte, algorithm EncryptionAlgorithm) (ciphertext []byte, nonce []byte, err error)
	Decrypt(ctx context.Context, handle string, data []byte, nonce []byte, algorithm EncryptionAlgorithm) ([]byte, error)
	Close() error
}
```

Add:

```go
// ImportKey imports externally-generated key material and returns an opaque
// handle in the same shape GenerateRSAKey/GenerateECDSAKey return — PEM for
// SoftwareKeyProvider, a CKA_LABEL for PKCS11KeyProvider. keyType is "RSA" or
// "ECDSA", matching CreateKeyRequest.Type.
ImportKey(ctx context.Context, keyType string, privateKey crypto.PrivateKey) (handle string, err error)
```

Implementations:

- **`SoftwareKeyProvider`** (`internal/crypto/software_provider.go`): mirror
  `GenerateRSAKey`/`GenerateECDSAKey`'s existing "handle is PEM" contract —
  PEM-encode `privateKey` (`*rsa.PrivateKey` or `*ecdsa.PrivateKey`) via
  `x509.MarshalPKCS8PrivateKey` + `pem.EncodeToMemory`, return the PEM string as
  the handle. No new state; this is a pure encode.
- **`PKCS11KeyProvider`** (`internal/crypto/pkcs11_provider.go`): import the raw
  key components onto the token via `C_CreateObject`, building the same attribute
  template `GenerateRSAKey`/`GenerateECDSAKey` use for `privAttrs`
  (`pkcs11_provider.go:153`, `:222`) — critically including
  `CKA_EXTRACTABLE: false` and `CKA_SENSITIVE: true` on the imported object, not
  just the generated ones. This is the load-bearing line for the "import is not an
  export backdoor" goal: once imported, the token enforces the same
  non-extractability on this key as on any key it generated itself. Return the new
  object's `CKA_LABEL` as the handle, same shape `GenerateRSAKey` returns.

### 2. JWK parsing — use `go-jose/go-jose/v4`, not hand-rolled

**Decision**: parse imported JWKs with `go-jose/go-jose/v4`'s `jose.JSONWebKey`,
not a hand-rolled RFC 7517 parser.

Reasoning:

- `go-jose/go-jose/v4 v4.1.4` is already a direct `go.mod` dependency (currently
  used only in `internal/services/auth/oidc_service_test.go` for OIDC token
  validation) — using it here adds no new dependency, only a new use of an
  existing one.
- `jose.JSONWebKey.UnmarshalJSON` already validates key-type-specific required
  fields (RSA CRT components `d`/`p`/`q`/`dp`/`dq`/`qi`, EC `crv`/`x`/`y`/`d`) per
  RFC 7517/7518 and exposes the parsed material via its `.Key` field as a typed
  `crypto.PrivateKey`. Hand-rolling this parser would mean re-implementing a spec
  with enough edge cases (base64url padding variants, curve validation, CRT vs.
  non-CRT RSA representations) that getting it wrong risks the same class of bug
  `.claude/known-bugs.md` § B42 describes for hand-rolled CSV — subtle, silent
  corruption on malformed-but-plausible-looking input.
- `internal/signing/jwks.go`'s existing helpers (`RSAPublicKeyToJWK`,
  `ECDSAPublicKeyToJWK`, `PublicKeyInfoToJWK`) are marshal-only and don't
  establish a hand-rolled-parsing precedent to follow — they're a different
  direction of the same problem, not a template for this one.

Add a new file, `internal/signing/jwk_parse.go`, sibling to the existing
marshal-only `jwks.go` (parse and marshal stay in the same package for
discoverability, split by file for clarity of direction):

```go
// ParseJWK parses a JWK containing private key material and returns the
// concrete Go key together with its RocketVault key-type string ("RSA" or
// "ECDSA"). It rejects public-only JWKs (no private component) and any kty/crv
// combination RocketVault does not support.
func ParseJWK(jwkJSON []byte) (privateKey crypto.PrivateKey, keyType string, err error) {
	var jwk jose.JSONWebKey
	if err := json.Unmarshal(jwkJSON, &jwk); err != nil {
		return nil, "", fmt.Errorf("invalid JWK: %w", err)
	}
	if !jwk.IsPublic() == false { /* placeholder — see note below */ }
	switch key := jwk.Key.(type) {
	case *rsa.PrivateKey:
		return key, "RSA", nil
	case *ecdsa.PrivateKey:
		return key, "ECDSA", nil
	default:
		return nil, "", fmt.Errorf("unsupported or public-only JWK (kty=%s)", jwk.KeyType())
	}
}
```

(The exact `IsPublic`-style guard should be written against `go-jose`'s real API
at implementation time — the point fixed here is the behavior: reject a JWK whose
`.Key` is not a concrete private key type, with a clear error, before it reaches
`crypto.KeyProvider.ImportKey`.)

`ParseJWK` is the only place the codebase depends on `go-jose`'s types directly;
`KeyService.ImportKey` depends on RocketVault's own function signature, keeping
the dependency swappable later without touching the service layer.

### 3. `KeyService` interface — add `ImportKey`

`internal/services/keys/key_service.go:95-144` groups the key-creation-shaped
methods (`CreateRSAKey`, `CreateECDSAKey`, `CreateOctKey`) at the top of the
interface. Add `ImportKey` alongside them:

```go
type KeyService interface {
	CreateRSAKey(ctx context.Context, req CreateKeyRequest) (*CreateKeyResult, error)
	CreateECDSAKey(ctx context.Context, req CreateKeyRequest) (*CreateKeyResult, error)
	CreateOctKey(ctx context.Context, req CreateKeyRequest) (*CreateKeyResult, error)
	// ImportKey stores externally-generated key material supplied as a JWK.
	// The imported key is subject to the same non-extractability guarantee as
	// a generated key of the same backend — see
	// docs/superpowers/specs/2026-08-25-key-export-decision-record.md.
	ImportKey(ctx context.Context, req ImportKeyRequest) (*CreateKeyResult, error)

	GetKey(ctx context.Context, keyID uuid.UUID, scope model.Scope) (*model.Key, error)
	// ... rest of the interface unchanged
}
```

New request type, next to `CreateKeyRequest` (`key_service.go:44-58`), reusing
its field shape:

```go
// ImportKeyRequest represents a request to import externally-generated key
// material supplied as a JWK.
type ImportKeyRequest struct {
	Name      string
	JWK       []byte // raw JWK JSON, parsed via signing.ParseJWK
	Tags      []string
	UserID    uuid.UUID
	VaultID   uuid.UUID
	Enabled   *bool
	ExpiresAt *time.Time
	NotBefore *time.Time
	PurgeProtection *bool
}
```

### 4. `keyService.ImportKey` implementation

Template directly off `CreateRSAKey` (`key_service.go:231-312`), substituting
step 2 (generation) for parse + provider-import:

```go
func (s *keyService) ImportKey(ctx context.Context, req ImportKeyRequest) (*CreateKeyResult, error) {
	logrus.WithFields(logrus.Fields{
		"name":    req.Name,
		"user_id": req.UserID.String(),
	}).Info("Importing key")

	privateKey, keyType, err := signing.ParseJWK(req.JWK)
	if err != nil {
		s.logger.LogAuditError(req.UserID.String(), "import_key", "failed", "invalid JWK", err)
		return nil, fmt.Errorf("invalid JWK: %w", err)
	}

	handle, err := s.keyProvider.ImportKey(ctx, keyType, privateKey)
	if err != nil {
		s.logger.LogAuditError(req.UserID.String(), "import_key", "failed", "failed to import key material", err)
		return nil, fmt.Errorf("failed to import key: %w", err)
	}

	// Same isPKCS11Handle branch every Create*Key method uses.
	var storedValue string
	if isPKCS11Handle(handle) {
		storedValue = "pkcs11:" + handle
	} else {
		storedValue, err = common.EncryptSecret(handle)
		if err != nil {
			s.logger.LogAuditError(req.UserID.String(), "import_key", "failed", "failed to encrypt key", err)
			return nil, fmt.Errorf("failed to encrypt key: %w", err)
		}
	}

	enabled := true
	if req.Enabled != nil {
		enabled = *req.Enabled
	}

	key := &model.Key{
		ID:        uuid.New(),
		UserID:    req.UserID,
		VaultID:   resolveVaultID(req.VaultID),
		Name:      req.Name,
		Type:      keyTypeFor(keyType), // model.KeyTypeRSA / model.KeyTypeECDSA
		Value:     storedValue,
		Revoked:   false,
		CreatedAt: time.Now(),
		Tags:      req.Tags,
		Enabled:   enabled,
		ExpiresAt: req.ExpiresAt,
		NotBefore: req.NotBefore,
	}

	if err := s.keyRepo.Create(ctx, key); err != nil {
		s.logger.LogAuditError(req.UserID.String(), "import_key", "failed", "failed to store key", err)
		return nil, fmt.Errorf("failed to store imported key: %w", err)
	}

	if err := s.applyCreatePurgeProtection(ctx, /* adapt CreateKeyRequest-shaped call */, key.ID, "import_key"); err != nil {
		return nil, err
	}

	s.logger.LogAuditInfo(req.UserID.String(), "import_key", "success", fmt.Sprintf("key imported: %s, ID: %s", req.Name, key.ID))

	return &CreateKeyResult{
		KeyID:     key.ID,
		Name:      key.Name,
		Type:      key.Type,
		Tags:      key.Tags,
		CreatedAt: key.CreatedAt,
	}, nil
}
```

`applyCreatePurgeProtection` currently takes a `CreateKeyRequest` — at
implementation time, either widen its signature to accept just the
`PurgeProtection *bool` field it actually needs, or add a second thin wrapper.
This is a small refactor, not a design decision that needs resolving here.

### 5. `retry.RetryKeyService` passthrough

`internal/services/retry/retry_key_service.go` defines
`type RetryKeyService interface { keys.KeyService }` — a decorator that must
implement every `KeyService` method. Adding `ImportKey` to the interface forces a
compile error here until a passthrough is added, matching the existing
`CreateRSAKey` decorator shape:

```go
func (s *retryKeyService) ImportKey(ctx context.Context, req keys.ImportKeyRequest) (*keys.CreateKeyResult, error) {
	var result *keys.CreateKeyResult
	err := retried(ctx, s.retryService, func() error {
		var err error
		result, err = s.baseService.ImportKey(ctx, req)
		return err
	})
	return result, err
}
```

### 7. Route shape decision — collection-level `POST /keys/import`

Two shapes are possible: `POST /keys/{id}/import` (sub-resource, like
`rotate`/`backup`) or `POST /keys/import` (collection-level, like `create`).

**Decision: collection-level, `POST /keys/import`.** Import always creates a new
key — there is no existing `{id}` to nest under, the same reason `create` is
collection-level. This also matches Azure's own route shape,
`POST /keys/{name}/import`, where `{name}` is the *new* key's name, not a
reference to something already in the vault.

`mapKeyAction` (`internal/services/authorization/data_actions.go:140-208`)
currently handles the empty-`rest` case at lines 142-149 (`GET`→Read,
`POST`→Create) and the `"restore"` case at 150-154. Add a sibling:

```go
switch rest {
case "":
	switch method {
	case http.MethodGet:
		return model.ActionKeysRead, RouteVaultData
	case http.MethodPost:
		return model.ActionKeysCreate, RouteVaultData
	}
	return "", RouteVaultData
case "restore":
	if method == http.MethodPost {
		return model.ActionKeysRestore, RouteVaultData
	}
	return "", RouteVaultData
case "import":
	if method == http.MethodPost {
		return model.ActionKeysImport, RouteVaultData
	}
	return "", RouteVaultData
}
```

No new `DataAction` constant is needed — `ActionKeysImport` already exists
(`model/azure_roles.go:54`) and is already granted to
`RoleKeyVaultAdministrator`/`RoleKeyVaultCryptoOfficer`
(`model/azure_roles.go:161`, `:192`).

## Testing

Follow `internal/services/keys/key_service_extended_test.go`'s established
pattern: `mockKeyRepository` + either `mockKeyProviderForService` (for
validation/error-path tests) or a real `crypto.NewSoftwareKeyProvider()`
(for success-path tests, exercising the actual JWK→PEM→encrypt path), with
`setupKeyTestMasterKey()` called before anything that hits
`common.EncryptSecret`, constructed via `NewKeyService(KeyServiceConfig{...})`.

Cases:
- Valid RSA JWK import (software backend) — assert `*model.Key.Value` is
  `common.EncryptSecret`-encrypted PEM, decrypts back to the original key.
- Valid EC JWK import (software backend).
- Malformed JWK (invalid JSON, missing required fields) rejected before any
  provider call.
- Public-only JWK (no private component) rejected with a clear error — this is
  the case `ParseJWK`'s `default:` branch exists for.
- HSM-backend import: `PKCS11KeyProvider.ImportKey` round-trips (requires a
  SoftHSM2-backed test, matching `internal/crypto/pkcs11_provider_test.go`'s
  existing style) and the resulting object's `CKA_EXTRACTABLE` attribute reads
  `false` — this is the test that enforces the non-export guarantee from
  [2026-08-25-key-export-decision-record.md](2026-08-25-key-export-decision-record.md)
  actually holds for imported keys, not just generated ones.
- `retryKeyService.ImportKey` passthrough compiles and delegates (covered
  implicitly by the interface satisfying `RetryKeyService` — a missed
  passthrough is a compile error, not a runtime one).
- API test for `POST /keys/import` (decode, authz, response shape).
- CLI test for `keys import` (flag parsing, role gate, output).
