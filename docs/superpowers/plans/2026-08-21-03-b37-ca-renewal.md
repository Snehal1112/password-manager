# B37 — CA-Preserving Certificate Renewal Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `certificates renew` re-issue a CA-signed certificate through the same CA — preserving issuer and chain — instead of silently converting it to a self-signed CA certificate.

**Architecture:** The CA link a renewal needs is not stored anywhere today: `CreateCertificateRequest.CACertID` is consumed at creation and discarded, and neither `model.Certificate` nor the `certificates` table has a column for it. So the fix is three layers deep — persist `ca_cert_id` (model, schema, repository), have `CreateCASignedCertificate` write it and derive the CA key type from the CA key material instead of the hardcoded `"RSA"`, then branch `RenewCertificate` on it. Two supporting defects in `internal/crypto` are fixed first because the headline chain-verification test cannot pass without them: CA templates never set `KeyUsageCertSign`, and `CreateCASignedCertificatePEM` returns an empty certificate with a nil error for an unsupported CA key type.

**Tech Stack:** Go 1.24.2, `crypto/x509`, SQLite/PostgreSQL via `internal/db`, testify + testify/mock.

**Spec:** `docs/superpowers/specs/2026-08-21-cli-bug-fixes-b35-b41-design.md`

**Depends on:** `docs/superpowers/plans/2026-08-21-08-b43-ca-keyusage.md` (B43),
which **must land first**. It owns the CA `KeyUsageCertSign` fix that used to be
Task 1 here; the chain-verification assertions in Tasks 6 and 8 cannot pass
until it does. Task 1 below is a stub kept in place so the task numbering — and
every cross-reference to it — stays valid.

## Decisions taken while reading the code

These three were called out as "determine by reading the code". Each is
implemented and tested by a step below.

1. **Is the CA still reachable at renew time?** It may not be, and the renewal
   must **fail loudly rather than fall back to self-signing** — a silent
   downgrade is the entire bug. The CA is resolved with the same two calls
   `CreateCASignedCertificate` uses plus one more gate:
   `ValidateCertificateAccess` (scope predicate + owner comparison), then
   `GetCertificate` (which adds `IsAccessible()`). So a CA that was deleted,
   purged, moved out of scope, disabled, or has itself expired refuses the
   renewal with a message naming the CA. This is deliberately **stricter than
   create**, which uses `certRepo.Read` and therefore will still sign with an
   expired CA. The asymmetry is intentional: renewal exists to produce a
   usable certificate, and one signed by an expired CA cannot chain-verify.
   Aligning create is a follow-up, noted in Task 10, not done here.
2. **Must renewing a self-signed CA certificate keep `IsCA: true`?** Yes.
   `CreateSelfSignedCertificate` sets `IsCA: true` unconditionally
   (`certificate_service.go:230`) for *every* self-signed certificate, so the
   self-signed renewal branch keeps `IsCA: true` to match create exactly.
   Dropping it would strip the CA bit from every CA this system ever issued
   the moment it renewed, which is a worse bug than B37. (That blanket
   `IsCA: true` on self-signed leaf certificates is itself questionable, but it
   is create's contract and out of scope — noted in Task 10.)
3. **Keep refusing to renew an expired certificate?** Yes, deliberately.
   `RenewCertificate` reaches the original through `GetCertificate`, which
   enforces `IsAccessible()`, so a disabled, not-yet-valid or expired
   certificate cannot be renewed. Preserved because: changing it is a behavior
   change outside B37's scope; the CLI help already documents it ("renew
   before it lapses rather than after"); and `CheckAndRenewCertificates`
   independently skips already-expired certificates
   (`renewal_service.go:58-63`), so the two paths agree. Task 8 pins it with a
   regression test so a later change is a conscious one.

## What the spec got wrong or left open

Recorded here so the implementer does not trust the spec over the code:

- The spec says "Branch on the original's `CACertID`". **There is no such
  field.** `model.Certificate` has no `CACertID`, the `certificates` table has
  no `ca_cert_id` column, and `CreateCASignedCertificate` never persists
  `req.CACertID`. Tasks 4–6 add the whole storage path; without them the
  branch has nothing to branch on.
- Consequently every **pre-existing** CA-signed certificate has a NULL CA
  link and cannot be renewed correctly. Task 7 adds a guard: when `CACertID`
  is nil but the stored body is *not* self-signed, the renewal is refused with
  an actionable error instead of silently self-signing.
- The spec says to derive the CA key type from "the CA key's own `Type`
  field". The CA key row is not necessarily reachable (`caCert.KeyID` is empty
  on rows predating the `key_id` migration, and the key may have been purged
  while the certificate survives), while the CA's private key PEM is already
  decrypted in hand. Task 3 derives the type from that PEM instead, which is
  strictly more authoritative — it describes the key that will actually sign —
  and needs no extra read or failure mode. The spec's intent (stop hardcoding
  `"RSA"`) is honored.
- The spec's headline test says the chain must verify with `CheckSignatureFrom`
  or a pool `Verify`. **Neither can pass today**: `CreateX509Template` sets
  `KeyUsage` to `DigitalSignature|KeyEncipherment` with no `KeyUsageCertSign`,
  and both Go APIs reject a non-zero parent `KeyUsage` lacking `CertSign` with
  a `ConstraintViolationError`. That is bug B43, fixed by
  `docs/superpowers/plans/2026-08-21-08-b43-ca-keyusage.md`, which must land
  before this plan.
- `CreateCASignedCertificatePEM`'s inner type switches have no `default`, so a
  CA key that is neither `*rsa.PrivateKey` nor `*ecdsa.PrivateKey` (an
  `ES256K` CA) leaves `certBytes` nil with `err` nil and the function returns a
  PEM block wrapping zero bytes — a bogus certificate, no error. Task 2 closes
  it.

```go
// DetectPrivateKeyType reports the type of a PEM-encoded private key, using
// the same vocabulary ParsePrivateKey accepts. It reads the key material
// itself rather than a stored type string, so it cannot disagree with the key
// that will actually sign.
//
// Parameters:
//   - pemData: The PEM-encoded private key.
//
// Returns:
//
//	"RSA", "ECDSA" or "ES256K", or an error if the key cannot be classified.
func DetectPrivateKeyType(pemData string) (string, error) {
	block, _ := pem.Decode([]byte(pemData))
	if block == nil {
		return "", fmt.Errorf("failed to decode private key PEM")
	}

	switch block.Type {
	case "RSA PRIVATE KEY":
		return "RSA", nil
	case "EC PRIVATE KEY":
		// secp256k1 keys use this block type too, but MarshalSecp256k1PrivateKeyPEM
		// writes a raw 32-byte scalar rather than SEC1 DER, so a parse failure
		// identifies them.
		if _, err := x509.ParseECPrivateKey(block.Bytes); err == nil {
			return "ECDSA", nil
		}
		return "ES256K", nil
	default:
		return "", fmt.Errorf("unsupported private key PEM block type: %s", block.Type)
	}
}
```

```go
package certificates

import (
	"crypto/x509"
	"encoding/pem"
	"testing"

	"github.com/stretchr/testify/require"
)

// parseCertPEM decodes and parses one PEM-encoded certificate.
func parseCertPEM(t *testing.T, certPEM string) *x509.Certificate {
	t.Helper()
	block, _ := pem.Decode([]byte(certPEM))
	require.NotNil(t, block, "certificate PEM must decode")
	cert, err := x509.ParseCertificate(block.Bytes)
	require.NoError(t, err)
	return cert
}

// assertSignedBy proves that leafPEM was issued by caPEM: the issuer common
// name matches, the CA's own signature check accepts the leaf, and the leaf
// chains to the CA as a root. All three, because an issuer field alone can be
// written by anyone -- it is the signature that makes the chain real.
func assertSignedBy(t *testing.T, leafPEM, caPEM, wantIssuerCN string) {
	t.Helper()

	leaf := parseCertPEM(t, leafPEM)
	ca := parseCertPEM(t, caPEM)

	require.Equal(t, wantIssuerCN, leaf.Issuer.CommonName, "issuer common name")
	require.NoError(t, leaf.CheckSignatureFrom(ca), "leaf must verify against the CA")

	pool := x509.NewCertPool()
	pool.AddCert(ca)
	_, err := leaf.Verify(x509.VerifyOptions{
		Roots:     pool,
		KeyUsages: []x509.ExtKeyUsage{x509.ExtKeyUsageAny},
	})
	require.NoError(t, err, "leaf must chain to the CA")
}

// assertSelfSigned proves a certificate is its own issuer and verifies against
// its own public key.
func assertSelfSigned(t *testing.T, certPEM string) {
	t.Helper()

	cert := parseCertPEM(t, certPEM)
	require.Equal(t, cert.Subject.CommonName, cert.Issuer.CommonName, "a self-signed certificate issues itself")
	require.NoError(t, cert.CheckSignature(cert.SignatureAlgorithm, cert.RawTBSCertificate, cert.Signature),
		"a self-signed certificate must verify against its own key")
}
```

```go
// renewCASignedBody re-issues a CA-signed certificate through the CA that
// signed the original, so the issuer and the chain survive the renewal.
//
// The CA is resolved with the same authorization CreateCASignedCertificate
// uses -- the scoped read plus the owner comparison -- and then read again
// through GetCertificate, which adds the lifecycle gate. A CA that was
// deleted, moved out of scope, disabled or has itself expired therefore
// refuses the renewal. That is deliberately stricter than creation, which
// will still sign with an expired CA: a renewal exists to produce a usable
// certificate, and one signed by an expired CA cannot chain-verify.
func (s *certificateService) renewCASignedBody(ctx context.Context, original *model.Certificate, scope model.Scope, privateKeyPEM, keyType string, validityDays int) (string, error) {
	userID := scope.ActorID()
	caCertID := *original.CACertID

	if err := s.ValidateCertificateAccess(ctx, caCertID, scope); err != nil {
		s.logger.LogAuditError(userID.String(), "renew_certificate", "failed", "cannot access signing CA certificate", err)
		return "", fmt.Errorf("cannot renew CA-signed certificate: signing CA %s is not accessible: %w", caCertID, err)
	}

	caCert, err := s.GetCertificate(ctx, caCertID, scope)
	if err != nil {
		s.logger.LogAuditError(userID.String(), "renew_certificate", "failed", "signing CA certificate is unusable", err)
		return "", fmt.Errorf("cannot renew CA-signed certificate: signing CA %s is unusable: %w", caCertID, err)
	}

	caKeyPEM, err := common.DecryptSecret(caCert.PrivateKey)
	if err != nil {
		s.logger.LogAuditError(userID.String(), "renew_certificate", "failed", "failed to decrypt CA key", err)
		return "", fmt.Errorf("failed to decrypt CA key: %w", err)
	}

	caKeyType, err := crypto.DetectPrivateKeyType(caKeyPEM)
	if err != nil {
		s.logger.LogAuditError(userID.String(), "renew_certificate", "failed", "failed to determine CA key type", err)
		return "", fmt.Errorf("failed to determine CA key type: %w", err)
	}

	certPEM, err := crypto.CreateCASignedCertificatePEM(privateKeyPEM, keyType, caCert.Certificate, caKeyPEM, caKeyType, crypto.CertificateTemplate{
		CommonName:   original.Name,
		ValidityDays: validityDays,
		IsCA:         false,
	})
	if err != nil {
		s.logger.LogAuditError(userID.String(), "renew_certificate", "failed", "failed to generate CA-signed certificate", err)
		return "", fmt.Errorf("failed to generate renewed certificate: %w", err)
	}
	return certPEM, nil
}

// isSelfSignedPEM reports whether a stored certificate signed itself, by
// checking its signature against its own public key.
func isSelfSignedPEM(certPEM string) (bool, error) {
	block, _ := pem.Decode([]byte(certPEM))
	if block == nil {
		return false, fmt.Errorf("failed to decode PEM block from certificate")
	}
	cert, err := x509.ParseCertificate(block.Bytes)
	if err != nil {
		return false, fmt.Errorf("failed to parse X.509 certificate: %w", err)
	}
	return cert.CheckSignature(cert.SignatureAlgorithm, cert.RawTBSCertificate, cert.Signature) == nil, nil
}
```

```markdown
was consumed at creation and discarded, and neither `model.Certificate` nor the
`certificates` table had a column for it. The fix therefore spans the storage
path as well as the branch:

- `certificates.ca_cert_id` added to the fresh-install schema and to
  `migrateSchema`; `model.Certificate.CACertID *uuid.UUID` added.
  `CertificateRepository.Update` deliberately does **not** write the column —
  renewal writes through it, and touching it there would erase the issuer.
- `CreateCASignedCertificate` records the link and derives the CA key type
  from the CA private key via the new `crypto.DetectPrivateKeyType`, replacing
  the hardcoded `"RSA"`.
- `RenewCertificate` branches on the link. A CA that is deleted, out of scope,
  disabled or expired refuses the renewal instead of silently self-signing —
  stricter than creation, deliberately.
- `crypto.CreateX509Template` now adds `KeyUsageCertSign|KeyUsageCRLSign` to
  CA templates. Without it neither `CheckSignatureFrom` nor a pool `Verify`
  accepted any chain this system issued, so the headline regression test could
  not have been written.
- `crypto.CreateCASignedCertificatePEM` now errors on an unsupported CA key
  type instead of returning a PEM block wrapping zero bytes with a nil error.

1. Certificates created before this change have a NULL `ca_cert_id`. If such a

2. CA certificates issued before this change lack `KeyUsageCertSign`, so

- `CreateCASignedCertificate` will still sign with an expired CA

- `CreateSelfSignedCertificate` sets `IsCA: true` on every self-signed
```
