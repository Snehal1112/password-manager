# B43 — CA Certificate CertSign Key Usage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a CA certificate issued by RocketVault carry `KeyUsageCertSign | KeyUsageCRLSign` so that certificates signed by it actually verify against it.

**Architecture:** `crypto.CreateX509Template` builds one `x509.Certificate` template for both leaves and CAs, asserting a key-usage extension of `DigitalSignature|KeyEncipherment` regardless of `params.IsCA`. RFC 5280 requires a CA that asserts key usage to include `keyCertSign`, and `crypto/x509` enforces it, so every chain this system ever issued fails `CheckSignatureFrom` and `Verify`. The fix branches the `KeyUsage` value on `params.IsCA` inside that one function; both callers (`CreateSelfSignedCertificatePEM`, `CreateCASignedCertificatePEM`) pick it up with no signature change.

**Tech Stack:** Go 1.24.2, `crypto/x509`, `encoding/pem`, testify.

**Spec:** `docs/superpowers/specs/2026-08-21-cli-bug-fixes-b35-b41-design.md`

**Blocks:** `docs/superpowers/plans/2026-08-21-03-b37-ca-renewal.md`. That plan's
Task 1 previously owned this work and is now a stub pointing here; its
chain-verification tests (Tasks 6 and 8) cannot pass until this plan lands. Land
this plan first.

## Facts established by reading the code

Recorded so the implementer does not have to re-derive them.

1. **`CreateX509Template` is the only place a template is built.** Its two
   callers, `CreateSelfSignedCertificatePEM` (`x509_helper.go:88`) and
   `CreateCASignedCertificatePEM` (`x509_helper.go:155`), both call it and
   neither mutates the returned template. One edit fixes both paths.
2. **`CreateSelfSignedCertificate` passes `IsCA: true` unconditionally**
   (`internal/services/certificates/certificate_service.go:230`, and again on
   the renewal path at `:743`). So *every* self-signed certificate this service
   issues is a CA and will gain `CertSign|CRLSign` after this fix — not only the
   ones an operator intends as a CA. That blanket `IsCA: true` is create's
   existing contract and is **out of scope here** (plan 03 records it as a
   follow-up); this plan must not change it. It does mean the release note in
   Task 2 has to be worded for "every self-signed certificate", not "CAs only".
3. **`CreateCASignedCertificate` passes `IsCA: false`**
   (`certificate_service.go:384`), so leaves are unaffected by the fix. The
   negative test in Task 1 pins that.
4. **Nothing in the tree asserts on `KeyUsage` today.** `grep -rn "KeyUsage"
   --include="*_test.go"` matches only `common/context_test.go`, an unrelated
   context-key test. The existing certificate tests
   (`internal/crypto/crypto_edge_test.go:107-259`) assert only
   `Contains(certPEM, "CERTIFICATE")` and a common name — which is exactly why
   this survived. No existing expectation changes.
5. **`x509.CreateCertificate` does not police the parent's key usage.** It signs
   happily with a `CertSign`-less parent; only verification rejects the result.
   That is why issuance always "succeeded" while every chain was unusable.

```go
package crypto

import (
	"crypto/x509"
	"encoding/pem"
	"testing"

	"github.com/stretchr/testify/require"
)

// parseCertPEM decodes and parses one PEM-encoded certificate.
func parseCertPEM(t *testing.T, certPEM string) *x509.Certificate {
	t.Helper()

	block, _ := pem.Decode([]byte(certPEM))
	require.NotNil(t, block, "certificate PEM must decode")
	cert, err := x509.ParseCertificate(block.Bytes)
	require.NoError(t, err)
	return cert
}

// requireChainVerifies proves leafPEM was really issued by caPEM. Both checks
// matter: CheckSignatureFrom applies the issuer's own key and its CA
// constraints, and Verify additionally builds a chain to the CA as a trusted
// root, which is what a real client does.
func requireChainVerifies(t *testing.T, leafPEM, caPEM string) {
	t.Helper()

	leaf := parseCertPEM(t, leafPEM)
	ca := parseCertPEM(t, caPEM)

	require.NoError(t, leaf.CheckSignatureFrom(ca), "leaf must verify against its CA")

	pool := x509.NewCertPool()
	pool.AddCert(ca)
	chains, err := leaf.Verify(x509.VerifyOptions{Roots: pool})
	require.NoError(t, err, "leaf must chain to the CA as a trusted root")
	require.NotEmpty(t, chains)
}

// A CA certificate must carry KeyUsageCertSign. RFC 5280 requires it once a
// key-usage extension is asserted at all, and crypto/x509 enforces it.
func TestCreateX509Template_CAGetsCertSign(t *testing.T) {
	tmpl, err := CreateX509Template(CertificateTemplate{
		CommonName:   "ca.example.com",
		ValidityDays: 3650,
		IsCA:         true,
	})
	require.NoError(t, err)
	require.True(t, tmpl.IsCA)
	require.True(t, tmpl.BasicConstraintsValid)
	require.NotZero(t, tmpl.KeyUsage&x509.KeyUsageCertSign, "a CA template must allow certificate signing")
	require.NotZero(t, tmpl.KeyUsage&x509.KeyUsageCRLSign, "a CA template must allow CRL signing")
	require.NotZero(t, tmpl.KeyUsage&x509.KeyUsageDigitalSignature, "the existing usages must be kept")
	require.NotZero(t, tmpl.KeyUsage&x509.KeyUsageKeyEncipherment, "the existing usages must be kept")
}

// Regression guard: the fix must be conditional on IsCA. A leaf that gained
// certificate-signing authority would be a worse defect than the one being
// fixed, and a blanket KeyUsage change would pass the CA test above.
func TestCreateX509Template_LeafHasNoCertSign(t *testing.T) {
	tmpl, err := CreateX509Template(CertificateTemplate{
		CommonName:   "leaf.example.com",
		ValidityDays: 365,
		IsCA:         false,
	})
	require.NoError(t, err)
	require.False(t, tmpl.IsCA)
	require.Zero(t, tmpl.KeyUsage&x509.KeyUsageCertSign, "a leaf template must not allow certificate signing")
	require.Zero(t, tmpl.KeyUsage&x509.KeyUsageCRLSign, "a leaf template must not allow CRL signing")
}

// The headline test: an RSA CA issued by this package must be able to issue a
// leaf that passes both standard verification paths. Asserting on the usage
// bits alone would accept a wrong fix, so this asserts on the outcome.
func TestCASignedChain_RSACA_Verifies(t *testing.T) {
	caKeyPEM, err := GenerateRSAKeyPEM(2048)
	require.NoError(t, err)
	leafKeyPEM, err := GenerateRSAKeyPEM(2048)
	require.NoError(t, err)

	caPEM, err := CreateSelfSignedCertificatePEM(caKeyPEM, "RSA", CertificateTemplate{
		CommonName:   "rsa-ca.example.com",
		ValidityDays: 3650,
		IsCA:         true,
	})
	require.NoError(t, err)

	leafPEM, err := CreateCASignedCertificatePEM(leafKeyPEM, "RSA", caPEM, caKeyPEM, "RSA", CertificateTemplate{
		CommonName:   "leaf.example.com",
		ValidityDays: 365,
		IsCA:         false,
	})
	require.NoError(t, err)

	requireChainVerifies(t, leafPEM, caPEM)
}

// The same outcome must hold for an ECDSA CA, so the fix cannot be
// RSA-specific: it lives in the shared template, not in a signing branch.
func TestCASignedChain_ECDSACA_Verifies(t *testing.T) {
	caKeyPEM, err := GenerateECDSAKeyPEM("P-256")
	require.NoError(t, err)
	leafKeyPEM, err := GenerateECDSAKeyPEM("P-256")
	require.NoError(t, err)

	caPEM, err := CreateSelfSignedCertificatePEM(caKeyPEM, "ECDSA", CertificateTemplate{
		CommonName:   "ec-ca.example.com",
		ValidityDays: 3650,
		IsCA:         true,
	})
	require.NoError(t, err)

	leafPEM, err := CreateCASignedCertificatePEM(leafKeyPEM, "ECDSA", caPEM, caKeyPEM, "ECDSA", CertificateTemplate{
		CommonName:   "ec-leaf.example.com",
		ValidityDays: 365,
		IsCA:         false,
	})
	require.NoError(t, err)

	requireChainVerifies(t, leafPEM, caPEM)
}

// An issued CA certificate must carry the usage in its signed body, not just
// in the in-memory template -- that is the part an already-issued certificate
// can never gain.
func TestSelfSignedCA_CarriesCertSignInTheIssuedCertificate(t *testing.T) {
	caKeyPEM, err := GenerateRSAKeyPEM(2048)
	require.NoError(t, err)

	caPEM, err := CreateSelfSignedCertificatePEM(caKeyPEM, "RSA", CertificateTemplate{
		CommonName:   "issued-ca.example.com",
		ValidityDays: 3650,
		IsCA:         true,
	})
	require.NoError(t, err)

	ca := parseCertPEM(t, caPEM)
	require.True(t, ca.IsCA)
	require.True(t, ca.BasicConstraintsValid)
	require.NotZero(t, ca.KeyUsage&x509.KeyUsageCertSign)
	require.NotZero(t, ca.KeyUsage&x509.KeyUsageCRLSign)
}

```markdown
# v4.2.0 — CA certificates gain the certificate-signing key usage

Fixes a defect present in every release to date: certificates issued as CAs
did not assert the `keyCertSign` key usage, so nothing they signed could be
verified by a standards-conforming client. See `.claude/known-bugs.md` § B43.

## What was wrong

`crypto.CreateX509Template` built one X.509 template for leaves and CAs alike.
It set `IsCA` and `BasicConstraintsValid` from the request, but always set the
key usage to `digitalSignature | keyEncipherment`. RFC 5280 requires a CA that
asserts a key-usage extension to include `keyCertSign`, and Go's verifier,
OpenSSL and browsers all enforce it.

The consequence: `rocketvault certificates create --ca-cert-id ...` returned a
certificate that looked correct and had a valid signature, but

- `leaf.CheckSignatureFrom(ca)` failed with
  `x509: invalid signature: parent certificate cannot sign this kind of certificate`
- chain verification against the CA failed with
  `x509: certificate signed by unknown authority`

Issuance never reported an error, because `x509.CreateCertificate` does not
check the signing parent's key usage — only verification does.

## What changed

A certificate created with `IsCA` now asserts
`digitalSignature | keyEncipherment | keyCertSign | cRLSign`. Leaf
certificates are unchanged and still do **not** carry `keyCertSign`.

Note that RocketVault marks **every self-signed certificate** as a CA
(`CreateSelfSignedCertificate` sets `IsCA: true` unconditionally), so every
newly created or renewed self-signed certificate — not only the ones you use
as an issuer — now carries the two extra usage bits.

## Breaking: certificates issued before this release cannot be repaired

**Key usage is inside the signed certificate body. Upgrading does not change
a certificate that already exists**, and there is no migration that can. So:

- Every CA certificate issued by any earlier version stays unusable as an
  issuer, for its whole remaining lifetime.
- Every certificate signed by such a CA keeps chaining to an unusable issuer,
  and stays unverifiable even after you upgrade.

### Reissue procedure

1. Upgrade to this release. New issuance is correct from that moment on.
2. Reissue each CA certificate. Creating a certificate without `--ca-cert-id`
   produces a self-signed CA:

   ```bash
   rocketvault certificates create --vault <vault> --name <ca-common-name> \
     --key-id <ca-key-uuid> --validity-days 3650
   ```

   Reusing the same key is fine — only the certificate body needs to change.
3. Reissue every certificate that was signed by the old CA, pointing at the
   **new** CA certificate's ID:

   ```bash
   rocketvault certificates create --vault <vault> --name <common-name> \
     --key-id <key-uuid> --ca-cert-id <new-ca-cert-uuid> --validity-days 365
   ```

4. Distribute the new CA certificate to every trust store that held the old
   one, then retire the old certificates.

### Checking a certificate you already hold

```bash
openssl x509 -in cert.pem -noout -text | grep -A1 "X509v3 Key Usage"
```

A CA issued before this release shows `Digital Signature, Key Encipherment`.
A correctly issued one also shows `Certificate Sign, CRL Sign`.

## Why it went unnoticed

No test verified a chain. The certificate tests asserted that issuance
returned a PEM block and that fields round-tripped, never that the result
validated. The fix adds chain verification — `CheckSignatureFrom` plus a
cert-pool `Verify`, for RSA and ECDSA CAs — so the same class of defect
cannot return silently.
```
