# B43 + B44 — CA Key Usage and Explicit CA Opt-In Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a CA certificate issued by RocketVault carry
`KeyUsageCertSign | KeyUsageCRLSign` so that certificates signed by it actually
verify against it (B43), and make being a CA something a caller asks for
instead of something every self-signed certificate gets (B44). The two ship as
one change because B43's fix keys off the `IsCA` flag B44 sets wrongly.

**Architecture:** Two layers, one change.

*Service layer (B44).* `CreateSelfSignedCertificate`
(`certificate_service.go:230`) and `RenewCertificate` (`:746`) both pass
`IsCA: true` to `crypto.CreateSelfSignedCertificatePEM`, so every self-signed
certificate this system has ever issued asserts `CA:TRUE` — TLS server
certificates included — and no code path can produce a self-signed leaf.
Creation gains an opt-in (`CreateCertificateRequest.IsCA`, surfaced as the
`--is-ca` CLI flag and the `is_ca` API field) defaulting to false; renewal
stops forcing a value at all and reads the CA bit out of the certificate it is
replacing, so a leaf renews as a leaf and a CA renews as a CA.

*Crypto layer (B43).* `crypto.CreateX509Template` builds one `x509.Certificate`
template for both leaves and CAs, asserting a key-usage extension of
`DigitalSignature|KeyEncipherment` regardless of `params.IsCA`. RFC 5280
requires a CA that asserts key usage to include `keyCertSign`, and
`crypto/x509` enforces it, so every chain this system ever issued fails
`CheckSignatureFrom` and `Verify`. The fix branches the `KeyUsage` value on
`params.IsCA` inside that one function; both callers
(`CreateSelfSignedCertificatePEM`, `CreateCASignedCertificatePEM`) pick it up
with no signature change.

**Tech Stack:** Go 1.24.2, `crypto/x509`, `encoding/pem`, Cobra, testify +
testify/mock.

**Spec:** `docs/superpowers/specs/2026-08-21-cli-bug-fixes-b35-b41-design.md`

**Blocks:** `docs/superpowers/plans/2026-08-21-03-b37-ca-renewal.md`. That plan's
Task 1 previously owned the B43 work and is now a stub pointing here; its
chain-verification tests (Tasks 6 and 8) cannot pass until this plan lands, and

Land this plan first.

## Task ordering is a security property — do not reorder

**Task 1 (B44's `IsCA` default) must land before Task 3 (B43's `CertSign`
addition), or in the same commit. Never the other way round.**

Why: B43's fix adds `CertSign|CRLSign` *conditioned on `IsCA`*. Today every
self-signed certificate carries `IsCA: true` with no `CertSign`, which is
exactly why verifiers refuse to treat one as a signer — the B43 defect is
accidentally the only thing stopping every self-signed leaf from working as a
CA. Landing Task 3 first would hand every self-signed certificate in the system
real certificate-signing authority: a leaked leaf key could then mint
certificates for arbitrary names. That is a security regression introduced by a
security fix.

Task 2 (the CLI and API opt-in) also belongs before Task 3, so that by the time
`CertSign` starts working the only way to get a CA is to have asked for one.

The task order below is therefore: **B44 default → B44 opt-in → B43 CertSign →
docs → close bugs.** If a step fails and you are tempted to skip ahead, stop
instead. The intermediate state after Task 1 and before Task 3 is safe (no CA
can sign anything, exactly as today); the intermediate state after Task 3 and
before Task 1 is not.

## Facts established by reading the code

Recorded so the implementer does not have to re-derive them.

1. **`CreateX509Template` is the only place a template is built.** Its two
   callers, `CreateSelfSignedCertificatePEM` (`x509_helper.go:88`) and
   `CreateCASignedCertificatePEM` (`x509_helper.go:155`), both call it and
   neither mutates the returned template. One edit fixes both paths.
2. **There are exactly three `IsCA` call sites in non-test code**
   (`grep -rn "IsCA" --include="*.go" . | grep -v _test.go`):
   `certificate_service.go:230` (self-signed creation, `true`), `:384`
   (CA-signed creation, `false`) and `:746` (renewal, `true`). Task 1 changes
   the first and the third. `:384` stays `false` — issuing an intermediate CA
   is a separate feature, and Task 1 refuses the combination rather than
   ignoring it.
3. **The service request type is `certificates.CreateCertificateRequest`**
   (`internal/services/certificates/certificate_service.go:33-48`), and it is
   what both surfaces build. The HTTP body type is
   `api.CreateCertificateAPIRequest` (`api/certificates.go:40-53`).
   `model.CreateCertificateRequest` (`model/certificate.go:58-71`) looks like
   the API type but is **vestigial**: nothing outside `model/model_test.go`
   references it or `CreateCertificateRequestFromJson`. Do not add the new
   field there — it would be dead on arrival and would read as the real
   contract to the next person.
4. **Flag names mirror JSON field names exactly** in this command:
   `--ca-cert-id`/`ca_cert_id`, `--auto-renew`/`auto_renew`,
   `--purge-protection`/`purge_protection`, `--validity-days`/`validity_days`.
   The opt-in is therefore `--is-ca` / `is_ca`, not the bare `--ca` of B44's
   fix sketch: `--ca` would break that pairing and sit one character away from
   the command's own `--ca-cert-id` and the root command's `--ca-cert`, which
   takes a path. `pflag` does no prefix matching, so `--ca` would not be
   *ambiguous* — just easy to mistype into a different meaning.
5. **Boolean flags on this command are not bound to viper.** `--auto-renew`
   and `--purge-protection` are read with `cmd.Flags().GetBool`, while the
   string flags go through `viper.BindPFlag("cert-*")`. `--is-ca` follows the
   booleans: a viper binding is global state shared with every other command.
6. **`CreateSelfSignedCertificate` passes `IsCA: true` unconditionally**, so
   *every* self-signed certificate is a CA today. The release note in Task 4
   has to be worded for "every self-signed certificate", not "CAs only", and
   has to tell operators that a certificate already issued cannot be repaired.
7. **Nothing in the tree asserts on `KeyUsage` or `IsCA` today.**
   `grep -rn "KeyUsage" --include="*_test.go"` matches only
   `common/context_test.go`, an unrelated context-key test. The existing
   certificate tests (`internal/crypto/crypto_edge_test.go:107-259`) assert
   only `Contains(certPEM, "CERTIFICATE")` and a common name — which is
   exactly why both bugs survived.
8. **`x509.CreateCertificate` does not police the parent's key usage.** It
   signs happily with a `CertSign`-less parent; only verification rejects the
   result. That is why issuance always "succeeded" while every chain was
   unusable.
9. **One existing fixture stores an empty certificate body.**
   `TestRenewCertificate_Succeeds_WhenKeyIDSet`
   (`internal/services/certificates/cert_soft_delete_test.go:250-330`) builds
   `existingCert` with no `Certificate` field. Renewal now reads the CA bit out
   of that body, so the fixture breaks and Task 1 fixes it. No real row is ever
   empty. Plan 03's Task 7 Step 1 makes the same fixture change for its own
   reason — after this plan lands it will already be done (with `IsCA: false`,
   deliberately).
10. **Test-helper name collision to avoid.** Plan 03's Task 6 Step 2 creates
    `internal/services/certificates/chain_assert_test.go` declaring
    `parseCertPEM` in package `certificates`. The new test file below therefore
    names its own helper `parseIssuedCert`. Do not rename it to `parseCertPEM`;
    the package would stop compiling once plan 03 lands.

// IsCA: true, so the first renewal turned any certificate into a CA (B44).

	f := newRenewalFixture(t, false)

	_, err := f.svc.RenewCertificate(context.Background(), f.certID, f.scope, 365)
	require.NoError(t, err)
	require.NotNil(t, f.capture.cert)

	assert.False(t, parseIssuedCert(t, f.capture.cert.Certificate).IsCA,

	require.NoError(t, err)
	require.NotNil(t, f.capture.cert)

	assert.True(t, parseIssuedCert(t, f.capture.cert.Certificate).IsCA,
		"renewing a CA must keep it a CA")
}

// certificateIsCA reports whether a stored certificate asserts the CA basic
// constraint. Renewal reads it out of the certificate it is replacing, so a
// leaf renews as a leaf and a CA renews as a CA -- neither value is forced.
//
// Parameters:
//   - certPEM: The PEM-encoded certificate.
//
// Returns:
//
//	Whether the certificate is a CA, or an error if it cannot be parsed.
func certificateIsCA(certPEM string) (bool, error) {
	block, _ := pem.Decode([]byte(certPEM))
	if block == nil {
		return false, fmt.Errorf("failed to decode PEM block from certificate")
	}
	cert, err := x509.ParseCertificate(block.Bytes)
	if err != nil {
		return false, fmt.Errorf("failed to parse X.509 certificate: %w", err)
	}
	return cert.IsCA, nil
}

// parseCertPEM decodes and parses one PEM-encoded certificate.
func parseCertPEM(t *testing.T, certPEM string) *x509.Certificate {
	t.Helper()

	block, _ := pem.Decode([]byte(certPEM))
	require.NotNil(t, block, "certificate PEM must decode")
	cert, err := x509.ParseCertificate(block.Bytes)
	require.NoError(t, err)
	return cert
}

// requireChainVerifies proves leafPEM was really issued by caPEM. Both checks
// matter: CheckSignatureFrom applies the issuer's own key and its CA
// constraints, and Verify additionally builds a chain to the CA as a trusted
// root, which is what a real client does.
func requireChainVerifies(t *testing.T, leafPEM, caPEM string) {
	t.Helper()

	leaf := parseCertPEM(t, leafPEM)
	ca := parseCertPEM(t, caPEM)

	require.NoError(t, leaf.CheckSignatureFrom(ca), "leaf must verify against its CA")

	pool := x509.NewCertPool()
	pool.AddCert(ca)
	chains, err := leaf.Verify(x509.VerifyOptions{Roots: pool})
	require.NoError(t, err, "leaf must chain to the CA as a trusted root")
	require.NotEmpty(t, chains)
}

```markdown
# v4.2.0 — CA certificates: signing key usage, and CA status by request only

Two defects present in every release to date, fixed together because fixing
either alone would have made the other worse. See `.claude/known-bugs.md`
§ B43 and § B44.

- Certificates issued as CAs did not assert the `keyCertSign` key usage, so
  nothing they signed could be verified by a standards-conforming client.
- Every self-signed certificate was issued as a Certificate Authority,
  including ordinary TLS server certificates, with no way to ask for anything
  else.

## What was wrong

**No `keyCertSign` on a CA.** `crypto.CreateX509Template` built one X.509
template for leaves and CAs alike. It set `IsCA` and `BasicConstraintsValid`
from the request, but always set the key usage to
`digitalSignature | keyEncipherment`. RFC 5280 requires a CA that asserts a
key-usage extension to include `keyCertSign`, and Go's verifier, OpenSSL and
browsers all enforce it.

The consequence: `rocketvault certificate create --ca-cert-id ...` returned a
certificate that looked correct and had a valid signature, but

- `leaf.CheckSignatureFrom(ca)` failed with
  `x509: invalid signature: parent certificate cannot sign this kind of certificate`
- chain verification against the CA failed with
  `x509: certificate signed by unknown authority`

Issuance never reported an error, because `x509.CreateCertificate` does not
check the signing parent's key usage — only verification does.

**Every self-signed certificate was a CA.** Both self-signed code paths —
creation and renewal — passed `IsCA: true` unconditionally, and neither the
API nor the CLI exposed any way to request otherwise. So a certificate issued
for a web server carried `Basic Constraints: CA:TRUE`. To any party that
trusts such a certificate, its holder is an issuer: if the private key leaks,
the holder can mint certificates for arbitrary names.

The two defects held each other in place. A certificate marked `CA:TRUE`
without `keyCertSign` is refused as a signer, so the first defect was
accidentally the only thing stopping the second from being exploitable. That
is why the fix for one could not ship without the fix for the other.

## What changed

- A certificate created with the CA option now asserts
  `digitalSignature | keyEncipherment | keyCertSign | cRLSign`. Leaf
  certificates are unchanged and still do **not** carry `keyCertSign`.
- A self-signed certificate is now an ordinary leaf unless you ask for a CA:
  `--is-ca` on `rocketvault certificate create`, or `"is_ca": true` in the
  `POST /certificates` body. It cannot be combined with `--ca-cert-id` /
  `ca_cert_id`; issuing an intermediate CA is not supported and the
  combination is rejected rather than quietly ignored.
- Renewal preserves what the certificate already was. A CA renews as a CA, a
  leaf renews as a leaf. Renewal never changes the CA status in either
  direction.

## Breaking: certificates issued before this release cannot be repaired

**Both the key usage and the CA flag live inside the signed certificate body.
Upgrading does not change a certificate that already exists**, and there is no
migration that can. So:

- Every CA certificate issued by any earlier version stays unusable as an
  issuer, for its whole remaining lifetime.
- Every certificate signed by such a CA keeps chaining to an unusable issuer,
  and stays unverifiable even after you upgrade.
- Every self-signed certificate issued by any earlier version keeps asserting
  `CA:TRUE`, whatever it was meant to be. Upgrading does not narrow it. Treat
  the private key of any such certificate as issuer-grade material until the
  certificate is replaced.

### Reissue procedure

1. Upgrade to this release. New issuance is correct from that moment on.
2. Reissue each CA certificate, now asking for a CA explicitly:

   ```bash
   rocketvault certificate create --vault <vault> --name <ca-common-name> \
     --key-id <ca-key-uuid> --is-ca --validity-days 3650
   ```

   Reusing the same key is fine — only the certificate body needs to change.
3. Reissue every certificate that was signed by the old CA, pointing at the
   **new** CA certificate's ID:

   ```bash
   rocketvault certificate create --vault <vault> --name <common-name> \
     --key-id <key-uuid> --ca-cert-id <new-ca-cert-uuid> --validity-days 365
   ```

4. Reissue every self-signed certificate that was never meant to be a CA —
   omit `--is-ca` this time:

   ```bash
   rocketvault certificate create --vault <vault> --name <common-name> \
     --key-id <key-uuid> --validity-days 365
   ```

   Renewing such a certificate is **not** enough on its own: renewal preserves
   the CA flag the old certificate carries, by design, so an over-broad
   certificate stays over-broad until it is reissued.
5. Distribute the new CA certificate to every trust store that held the old
   one, then retire the old certificates.

### Checking a certificate you already hold

```bash
openssl x509 -in cert.pem -noout -text | grep -A1 -e "X509v3 Key Usage" -e "Basic Constraints"
```

- A CA issued before this release shows `CA:TRUE` with a key usage of
  `Digital Signature, Key Encipherment` and no `Certificate Sign`.
- A correctly issued CA shows `CA:TRUE` and `Certificate Sign, CRL Sign`.
- A correctly issued ordinary certificate shows `CA:FALSE` and no
  `Certificate Sign`. Anything showing `CA:TRUE` that you did not ask to be a
  CA predates this release and should be reissued.

## Why it went unnoticed

No test verified a chain, and no test asserted on `IsCA` or on key usage at
all. The certificate tests asserted that issuance returned a PEM block and
that fields round-tripped, never that the result validated or that it claimed
no more authority than it needed. The fix adds both: chain verification
(`CheckSignatureFrom` plus a cert-pool `Verify`, for RSA and ECDSA CAs) and
assertions that an ordinary certificate is a leaf with no signing authority,
so the same class of defect cannot return silently.
```
