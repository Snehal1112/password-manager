v4.3.0 — Passphrase-encrypted export and import via the API

docs/release-notes/v4.3.0-api-secrets-passphrase.md
On this page

POST /secrets/export and POST /secrets/import now support passphrase-encrypted exports directly, closing the gap left by v4.2.0's POST /secrets/export rejecting "encrypt": true outright (.claude/known-bugs.md § B36's 2026-08-22 follow-up note, § B51). Full design decision: docs/superpowers/specs/2026-08-21-cli-bug-fixes-b35-b41-design.md's "Decision (2026-08-21)" note, retroactively implemented on this date.

What changed

POST /secrets/export accepts a passphrase field alongside "encrypt": true in its JSON body and returns a sealed envelope — the same argon2id + AES-256-GCM format rocketvault secrets export --encrypt produces, not a second implementation. A non-empty passphrase alone (with encrypt omitted or false) still triggers encryption; encrypt: true is the clearer, recommended way to ask for one but is not itself required.

POST /secrets/import accepts a passphrase multipart form field, used only when the uploaded file is a sealed export — detected automatically by content, the same way rocketvault secrets import detects it. There is no separate "encrypted" flag; submitting a passphrase for a plaintext upload is simply ignored.

Both directions honor the API's existing authorization checks unchanged — this is a request/response shape change, not an authorization change.

Not breaking

Existing callers sending plaintext bodies (encrypt omitted or false) are completely unaffected — same request shape, same plaintext response. Existing callers already sending "encrypt": true with no passphrase still get a 400; only the error message text changed, from "encrypted export is available only through the CLI" to a passphrase-required message. That is a message change, not a new failure mode — the request already failed before this release too.

Where the passphrase comes from

Unlike the CLI, which resolves a passphrase from --passphrase-file, the ROCKETVAULT_EXPORT_PASSPHRASE environment variable, or an interactive prompt, in that order, the API has exactly one channel: the request body field (export) or form value (import). Callers are responsible for their own passphrase storage and transport — this relies on transport security (TLS) the same way every other credential-bearing endpoint in this API already does (e.g. POST /users/login's password). No minimum passphrase length is enforced at any layer; only non-empty is required, matching the CLI exactly.

Symmetry with the CLI

An export produced via the API can be imported via the CLI, and an export produced via the CLI can be imported via the API — same envelope format (common/export_envelope.go), same argon2id/AES-256-GCM primitives, no format version bump. The passphrase is never logged, echoed back in a response, or included in an audit record — only whether encryption occurred (a boolean) is recorded, matching how the CLI path has always handled this.
