This is release 2 of the two-release self-service provisioning plan release 1 started; full design: docs/superpowers/specs/2026-09-03-self-service-vault-provisioning-design.md. Release 1's note, docs/release-notes/v4.5.0-vault-provisioning.md, explained what a bounded provisioning grant is and ended with a forward notice promising exactly this change. This note is that promise kept.

The breaking change

A global (vault_id NULL) vaults:manage allow policy now confers create and list only. Its holder loses everything else it previously had over every vault on the instance, whether or not it created that vault — every one of the following is gated by CanManageVault or CanManageRoleAssignments against a concrete vault, and both now require a vault-scoped grant:

  1. Get, update, and delete on any vault it does not hold a vault-scoped grant over (internal/services/authorization.CanManageVault, api/vault.go, cmd/vaults/get.go, update.go, delete.go).
  2. Recover a soft-deleted vault (CanManageVault, cmd/vaults/recover.go) — CLI-only; there is no HTTP recover route.
  3. Vault-webhook configuration — get, set, and delete (CanManageVault, api/vault_webhook.go, cmd/vault-webhook/get.go, set.go, delete.go).
  4. Role-assignment management in any such vault (CanManageRoleAssignments) — which previously meant it could award itself Key Vault Administrator, or any other role, in a vault it had no other claim to.

An operator whose automation relies on a global grant to configure webhooks or recover soft-deleted vaults, not just to manage the vault record itself, needs the same remediation as the "Upgrade procedure" section below describes — those two are not a separate case.

Both functions were narrowed together, deliberately: narrowing only CanManageVault would have left the escalation open, since role-assignment management by itself is enough to self-award any role.

The admin account role is unaffected — it still short-circuits both functions before either policy check runs, exactly as before.

The mechanism is a new AccessPolicyService.CheckVaultScopedAccess (internal/services/authorization/access_policy_service.go), which the two functions now call whenever vaultID != uuid.Nil. It differs from CheckAccess in one respect: a NULL-scoped deny still matches (see below), but a NULL-scoped allow does not. The vaultID == uuid.Nil branch of CanManageVault — the real create/list decision — is untouched and still calls CheckAccess, so a global grant keeps working for what it is actually for. CanManageRoleAssignments has no such collection-level operation to serve — there is no "manage role assignments across every vault" — so its uuid.Nil branch always denies a non-admin caller (the admin account role still short-circuits above it, same as everywhere else in this function) rather than mirroring CanManageVault's; every call site already passes a resolved vault ID, so this is a closed door against a future mistake, not a behavior change today.

What did not change

A global explicit deny on (vaults, manage) still blocks every vault, including ones the denied principal created — the asymmetry between deny and allow is deliberate, not an oversight. CheckAccess and FindEffects are untouched by this release: PolicyMiddleware and cmd/vaultcli.RequireDataAction share them for the secrets/keys/certificates data plane, and both rely on FindEffects' (vault_id = ? OR vault_id IS NULL) match to make a global explicit deny work. Narrowing those two functions would have silently disabled every global deny on the data plane. A test now runs the real AccessPolicyService over the real repository against a NULL-scoped deny row specifically to pin this, because every pre-existing deny test stubbed the policy service and so could not have caught a leak.

Creator grants on the global-policy create path

Release 1 left this open explicitly: a global-policy holder creating a vault received none of the per-vault creator grants a provisioning-grant holder gets, because that was harmless while the global allow already covered every vault including the new one. It stops being harmless the moment the narrowing above lands — such a holder would create a vault it could no longer get, update, delete, or manage role assignments on.

This release resolves that open question. VaultService.CreateVaultProvisioned gained a grantCreatorRights parameter alongside the existing quotaBounded one. A global-policy holder now goes through the same transactional creator-granting path a provisioning grantee already uses — a vault-scoped vaults:manage access policy plus a Key Vault Administrator role assignment, written in the creation transaction — minus the quota check. The two booleans are derived from authz.CreateRight at every call site (api/vault.go, cmd/vaults/create.go): quotaBounded = right == CreateRightProvisioningGrant, grantCreatorRights = right != CreateRightAdmin. Admin creates are unchanged: the admin role short-circuits every authorization check, so creator grants for it would be dead rows, and it stays on the cheap non-transactional CreateVault path.

Purge protection: a three-tier distinction, not a widened guard

ErrPurgeProtectionNotPermitted and the CLI hint in cmd/vaults/create.go previously said purge protection "may only be set by an administrator". That was already imprecise before this release and is now actively misleading, because the guard itself has always been if quotaBounded && ... — it refuses only a quota-bounded create, not every non-admin one. Both messages have been reworded to name that predicate directly instead of "administrator". The behavior is unchanged; only the wording was wrong.

Concretely, three tiers now exist on the create path:

  • Admin: may set purge_protection on create. Unaffected by this release.
  • Global-policy holder: may also set it. It has no provisioning quota to pin, so the reason the restriction exists does not apply to it.
  • Provisioning grantee: refused at create time. A grantee who could set purge_protection at creation could soft-delete its own vault and hold its quota slot forever, since PurgeVault refuses to purge a protected vault and the slot is freed only by a purge.

This distinction was not an explicit product decision prior to this note — it falls out of reading quotaBounded's guard directly. It is recorded here deliberately, rather than left buried in an error string, so it can be reviewed and challenged rather than discovered by accident.

The create-time guard is a partial bound, not a full one. UpdateVault applies req.PurgeProtection with no quotaBounded predicate at all — it gates only on CanManageVault against the concrete vault. A provisioning grantee holds a vault-scoped vaults:manage allow over the vault it created (written by the creator-grant path this release adds), which satisfies CanManageVault for that vault. So a grantee refused purge_protection at vaults create can still reach it one command later: vaults create → vaults update --purge-protection → vaults delete — at which point the slot is held forever, exactly as the create-time guard exists to prevent, because PurgeVault refuses a protected vault for every caller including admin, and a soft-deleted vault still counts toward quota. This is a real, pre-existing defect — it shipped with release 1's quota enforcement, not with this release's narrowing, and is not fixed here; closing it means adding an equivalent guard to UpdateVault, which is follow-up work, tracked as .claude/known-bugs.md § B59.

Upgrade procedure

Before upgrading, run the previous release (v4.5.0) at least once and read its startup logs for warnGlobalVaultManageGrants (internal/db/db.go) warnings — it names every principal holding a NULL-scoped (vaults, manage, allow) policy, and every one of them loses everything listed under "The breaking change" above on this upgrade. For each principal it names, either:

  • Issue a bounded provisioning grant instead — rocketvault vault-provisioning grant <principal> --quota <n> — if the principal only ever needed to create and manage its own vaults, or
  • Add explicit vault-scoped vaults:manage access policies for the specific vaults it must keep managing, if it genuinely needs standing authority over vaults it did not create.

Existing vault-scoped grants (the common case for anyone who was already managing a bounded set of vaults deliberately) need no action — this release does not touch scoped policy evaluation.

Rollback

Reverting this release's commits restores the old semantics: a global vaults:manage allow goes back to covering get, update, delete, recover, webhook configuration, and role-assignment management on every vault. No schema change is involved on either side of the upgrade, so no data migration is needed in either direction.
