Two certificate defects present in every release to date, fixed together because fixing either alone would have made the other worse. See .claude/known-bugs.md § B43 and § B44. This release also makes rocketvault secrets export actually encrypt, closing a defect where the --encrypt flag claimed protection it never provided — see "Encrypted secret exports" below and .claude/known-bugs.md § B36.

  • Certificates issued as CAs did not assert the keyCertSign key usage, so nothing they signed could be verified by a standards-conforming client.
  • Every self-signed certificate was issued as a Certificate Authority, including ordinary TLS server certificates, with no way to ask for anything else.

What was wrong

No keyCertSign on a CA. crypto.CreateX509Template built one X.509 template for leaves and CAs alike. It set IsCA and BasicConstraintsValid from the request, but always set the key usage to digitalSignature | keyEncipherment. RFC 5280 requires a CA that asserts a key-usage extension to include keyCertSign, and Go's verifier, OpenSSL and browsers all enforce it.

The consequence: rocketvault certificate create --ca-cert-id ... returned a certificate that looked correct and had a valid signature, but

  • leaf.CheckSignatureFrom(ca) failed with x509: invalid signature: parent certificate cannot sign this kind of certificate
  • chain verification against the CA failed with x509: certificate signed by unknown authority

Issuance never reported an error, because x509.CreateCertificate does not check the signing parent's key usage — only verification does.

Every self-signed certificate was a CA. Both self-signed code paths — creation and renewal — passed IsCA: true unconditionally, and neither the API nor the CLI exposed any way to request otherwise. So a certificate issued for a web server carried Basic Constraints: CA:TRUE. To any party that trusts such a certificate, its holder is an issuer: if the private key leaks, the holder can mint certificates for arbitrary names.

The two defects held each other in place. A certificate marked CA:TRUE without keyCertSign is refused as a signer, so the first defect was accidentally the only thing stopping the second from being exploitable. That is why the fix for one could not ship without the fix for the other.

What changed

  • A certificate created with the CA option now asserts digitalSignature | keyEncipherment | keyCertSign | cRLSign. Leaf certificates are unchanged and still do not carry keyCertSign.
  • A self-signed certificate is now an ordinary leaf unless you ask for a CA: --is-ca on rocketvault certificate create, or "is_ca": true in the POST /certificates body. It cannot be combined with --ca-cert-id / ca_cert_id; issuing an intermediate CA is not supported and the combination is rejected rather than quietly ignored.
  • Renewal preserves what the certificate already was, with one deliberate exception. A CA issued by this release renews as a CA, a leaf renews as a leaf.
  • The exception is a certificate issued before this release: it asserts CA:TRUE but carries no keyCertSign, and that missing bit is the only reason it never worked as an issuer. Renewing it as a CA would hand it the keyCertSign the fixed template now adds and turn it into a fully working authority. Renewal therefore demotes such a certificate to an ordinary leaf and records the demotion in the audit log under the renew_certificate operation with status ca_demoted. Nothing is lost: nothing that certificate ever signed verified in the first place. If it was genuinely meant to be a CA, reissue it with --is-ca.

Breaking: certificates issued before this release cannot be repaired

Both the key usage and the CA flag live inside the signed certificate body. Upgrading does not change a certificate that already exists, and there is no migration that can. So:

  • Every CA certificate issued by any earlier version stays unusable as an issuer, for its whole remaining lifetime.
  • Every certificate signed by such a CA keeps chaining to an unusable issuer, and stays unverifiable even after you upgrade.
  • Every self-signed certificate issued by any earlier version keeps asserting CA:TRUE, whatever it was meant to be. Upgrading does not narrow it. Treat the private key of any such certificate as issuer-grade material until the certificate is replaced.

Reissue procedure

A certificate name is unique per vault, and that uniqueness is enforced by a plain unique index that does not exclude soft-deleted rows (idx_certificates_vault_name). A name is therefore not free for reuse until the old row is purged, not merely deleted. The procedure below gives the replacement CA a new name for that reason; see step 6 if you must keep the old name exactly.

  1. Upgrade to this release. New issuance is correct from that moment on.

  2. Reissue each CA certificate under a new name — a version or date suffix is enough — now asking for a CA explicitly:

    bash
    rocketvault certificate create --vault <vault> --name <ca-name>-2026 \
  --key-id <ca-key-uuid> --is-ca --validity-days 3650

    Reusing the same key is fine — only the certificate body needs to change. The name becomes the certificate's Subject CN, so pick one you are happy to see in a trust store. Keeping the old CA in place through the migration is deliberate: it is how you find what still chains to it.

  3. Reissue every certificate that was signed by the old CA, pointing at the new CA certificate's ID:

    bash
    rocketvault certificate create --vault <vault> --name <common-name> \
  --key-id <key-uuid> --ca-cert-id <new-ca-cert-uuid> --validity-days 365

  4. Reissue every self-signed certificate that was never meant to be a CA — omit --is-ca this time:

    bash
    rocketvault certificate create --vault <vault> --name <common-name> \
  --key-id <key-uuid> --validity-days 365

    Renewing such a certificate is not a substitute for reissuing it. Since the fix above, renewal demotes a pre-fix CA:TRUE certificate to an ordinary leaf and records ca_demoted in the audit log, so it no longer stays over-broad — but renewal keeps the same key and the same subject. A certificate that spent its whole life asserting CA:TRUE should have its private key treated as issuer-grade material, and demotion does not change that: only reissuing it gives it a new key.

  5. Distribute the new CA certificate to every trust store that held the old one, then retire the old certificates:

    bash
    rocketvault certificate delete <old-cert-id> --vault <vault>

    This is a soft delete: the certificate leaves certificate list and the background scheduler destroys it once the retention window ends.

  6. Only if you must keep the old name exactly. Soft-deleting does not free the name, so a same-named recreate fails on the unique index. Purge the old row first — a hard delete, with no recovery afterwards — and only then recreate under the old name. There is no CLI purge subcommand for certificates; purge is REST-only:

    bash
    curl -X DELETE -H "Authorization: Bearer $TOKEN" \
  https://<host>/api/v1/vaults/<vault>/deleted/certificates/<old-cert-id>/purge

    Do this only after step 3 has reissued everything that chained to the old CA — once the row is gone, so is the record of what it signed. A certificate with purge protection enabled refuses the purge; clear it with rocketvault certificate update <old-cert-id> --purge-protection=false before step 5's soft delete, not after — certificate update can only see a certificate that has not yet been soft-deleted. A vault with purge protection enabled needs its own flag cleared separately, via the vault update path, not the certificate command above. See .claude/known-bugs.md § B50.

Checking a certificate you already hold

bash
openssl x509 -in cert.pem -noout -text | grep -A1 -e "X509v3 Key Usage" -e "Basic Constraints"
  • A CA issued before this release shows CA:TRUE with a key usage of Digital Signature, Key Encipherment and no Certificate Sign.
  • A correctly issued CA shows CA:TRUE and Certificate Sign, CRL Sign.
  • A correctly issued ordinary certificate shows CA:FALSE and no Certificate Sign. Anything showing CA:TRUE that you did not ask to be a CA predates this release and should be reissued.

Why it went unnoticed

No test verified a chain, and no test asserted on IsCA or on key usage at all. The certificate tests asserted that issuance returned a PEM block and that fields round-tripped, never that the result validated or that it claimed no more authority than it needed. The fix adds both: chain verification (CheckSignatureFrom plus a cert-pool Verify, for RSA and ECDSA CAs) and assertions that an ordinary certificate is a leaf with no signing authority, so the same class of defect cannot return silently.

Encrypted secret exports

rocketvault secrets export now encrypts. The --encrypt flag has defaulted to true since it was introduced and was never read by any code, so every export written under it was plaintext (.claude/known-bugs.md § B36). Full design: docs/superpowers/specs/2026-08-21-cli-bug-fixes-b35-b41-design.md.

What an encrypted export is

A JSON envelope carrying an argon2id salt, the KDF parameters, and the export document sealed with AES-256-GCM under a key derived from your passphrase. The key is derived from the passphrase alone, never from the instance's master key, so an export can be opened by any RocketVault installation given the passphrase and survives a master-key rotate.

The envelope is JSON whatever --format you asked for; the format describes the payload inside it. A --format csv export is still imported with --format csv.

Where the passphrase comes from

In order: --passphrase-file <path> (first line, trimmed), then the ROCKETVAULT_EXPORT_PASSPHRASE environment variable, then an interactive prompt (asked twice on export, once on import).

Breaking: an export with no passphrase source now fails

A scripted export that supplies no passphrase and has no terminal — the common rocketvault secrets export --file secrets.json in a CI job or a cron entry — now fails and writes no file, where it previously wrote plaintext. This is deliberate: the previous behavior is the bug.

Two non-interactive escape hatches:

bash
# 1. A passphrase file, e.g. mounted from your own secret store
rocketvault secrets export --file secrets.json \
  --passphrase-file /run/secrets/export-pass

# 2. The environment variable
ROCKETVAULT_EXPORT_PASSPHRASE=… rocketvault secrets export --file secrets.json

If a downstream tool genuinely needs a readable file, ask for plaintext explicitly with --encrypt=false. The command then prints a warning naming what the file exposes — every secret's name, plaintext value and tags — and writes it anyway.

secrets import detects encryption

Import inspects the file's contents, so no flag tells it whether a file is encrypted. --encrypted is now redundant; it is deprecated and ignored, not removed, so existing invocations keep working. It will be removed in a later release.

Breaking: POST /secrets/export rejects "encrypt": true

Note (2026-08-22): this restriction was later lifted. See v4.3.0-api-secrets-passphrase.md — POST /secrets/export and POST /secrets/import now accept a passphrase field/form value and support encrypted export/import directly. The section below is left as written; it was accurate for this release.

The API's encrypt field was dead in the same way the CLI flag was. A request body is the wrong place to carry a passphrase, so the field is now rejected with 400 rather than silently returning plaintext. Encrypted export is CLI-only.

Exports written before this release

They are plaintext. Nothing in this release can change that retroactively — find them, treat every value in them as disclosed, and rotate accordingly. secrets import still reads them: a plaintext export is imported exactly as before, with no passphrase.
