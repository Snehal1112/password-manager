# v4.4.0 — Multi-role user assignment

A RocketVault user account can now hold more than one role at once. The
single `Role string` field on a user is replaced end-to-end — request bodies,
response bodies, JWT claims, the CLI, and the local RBAC permission
check — by a `Roles []string` field. Full design:
`docs/superpowers/specs/2026-08-23-multi-role-user-assignment-design.md`.

## What changed

`POST /users` and `PUT /users/{id}` now accept a JSON array field, `"roles":
[...]`, instead of the old `"role": "x"` string. The same rename applies to
every response that describes a user's roles: `POST /users` (create),
`GET /users` (list), `GET /users/{id}` (get), `POST /users/login`, and
`POST /users/refresh` all now return `"roles": [...]` in place of `"role"`.

## Breaking

This is a breaking change. Any client that builds a request body with
`"role": "x"` or reads a response's `"role"` field must be updated before
upgrading — there is no dual-field transition period.

A request that still sends the old `"role"` field is not silently ignored:
`createUser` and `updateUser` detect it and reject the request outright with
an HTTP 400 whose body reads:

```json
{
  "id": "Invalid or missing parameter: the \"role\" field was replaced by \"roles\": [...] in this API version",
  "message": "Invalid or missing parameter: the \"role\" field was replaced by \"roles\": [...] in this API version",
  "detailed_error": "",
  "status_code": 400,
  "request_id": "..."
}
```

This is a deliberate fail-fast: JSON decoding silently drops unknown fields
by default, which would otherwise have turned a still-`"role"`-shaped
request into a no-op that looked like it succeeded (200, with the account's
roles left unchanged) instead of surfacing the break.

### Migration example

Old request body (`POST /users`, `PUT /users/{id}`):

```json
{
  "username": "alice",
  "password": "alicepassword123",
  "role": "secrets_manager"
}
```

New request body — the same call, updated:

```json
{
  "username": "alice",
  "password": "alicepassword123",
  "roles": ["secrets_manager"]
}
```

A user can now be granted more than one role in the same request:

```json
{
  "username": "alice",
  "password": "alicepassword123",
  "roles": ["admin", "secrets_manager"]
}
```

## CLI: `--new-role` is repeatable

`rocketvault users create` and `rocketvault users update` already take a
`--new-role` flag; it is now a repeatable `StringArray` flag instead of a
single string. The old single-flag form still works unchanged
(`--new-role user` grants exactly that one role, same as before) — this is
additive, not a breaking CLI change. To grant more than one role in one
call, repeat the flag:

```
rocketvault users create \
  --username admin --password admin123 --totp-code 123456 \
  --new-username alice --new-password alicepassword123 \
  --new-role admin --new-role secrets_manager
```

See `docs/cli-guide.md`'s "Managing Users" section and `README.md` for
further examples.

## CLI output: the `Role` column is still a single string

`rocketvault users list` and `rocketvault users get` (in `-o table`, `-o
json`, and `-o yaml`) still emit a single `Role` column, now populated with
every role the account holds, comma-joined — for example `"admin,
secrets_manager"` — rather than a JSON array. This is because
`internal/formatter`'s `Write(headers []string, rows [][]string)` is
string-only; teaching it to emit a real array-typed column for one command's
output is out of scope for this release. If you consume `-o json`/`-o yaml`
output programmatically, split the `Role` field on `", "` to recover the
individual role names for now.

## Fixed (defense-in-depth): `RBACService.HasPermission`/`ValidateEndpointAccess` role-string handling

During this migration's own review, `RBACService.HasPermission` and
`ValidateEndpointAccess` were found and fixed to correctly evaluate
permissions against every role a caller holds, not just a single role
string. This is described here as a defense-in-depth fix discovered and
closed during the migration, not a disclosed vulnerability: at the point in
this migration series where the bug existed, `internal/middleware` did not
even compile (broken by an earlier step in the same series), so there was no
live, buildable production code path exercising it. Separately, the
production role-permission table's only route this check ever gated
(`/users`) already requires the global `admin` role regardless of this
check's correctness. No RocketVault deployment was ever exposed by this.

## Upgrade steps

1. Update any client code sending `"role": "x"` to `POST /users`/
   `PUT /users/{id}` to send `"roles": [...]` instead.
2. Update any client code reading `"role"` from a user-related response
   (`POST /users`, `GET /users`, `GET /users/{id}`, `POST /users/login`,
   `POST /users/refresh`) to read `"roles"` instead.
3. If you script `rocketvault users list`/`get -o json`/`-o yaml` output,
   change any code that expected a `Role` array to split the comma-joined
   `Role` string instead.
4. No manual database migration step is required. Storage moved to a new
   `user_roles` table (one row per user/role pair); `migrateSchema` creates
   it and backfills it from the existing `users.role` column automatically
   and idempotently on first startup after upgrading — the legacy `users.role`
   column is kept in sync on every subsequent create/update (a deliberate
   dual-write, which is what makes a binary rollback safe) but is never read
   by new code.
5. A pre-upgrade access token issued before this release still validates
   (its signing key, `kid`, and signature are untouched) for the remainder of
   its `jwt.expiry` lifetime (1h default — corrected 2026-09-04; this note
   originally said 15m, which understated the upgrade window fourfold. The
   key is optional and `internal/container/service_container.go` falls back
   to one hour), but it unmarshals to an empty
   roles list on the new binary — so admin-only GLOBAL routes (`/users`,
   `/audit/*`, `/oauth2/*`, `/jwks/rotate`) will 403 for existing sessions
   until the token expires or the user re-runs `rocketvault users login`.
   Per-vault DATA-PLANE access (secrets/keys/certificates) is unaffected by
   this: `PolicyMiddleware` authorizes those routes via the principal ID and
   the `role_assignments` table, not global roles, so this upgrade window has
   a much smaller blast radius than it might first appear.
