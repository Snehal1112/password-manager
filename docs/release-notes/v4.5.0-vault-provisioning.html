A non-admin principal can now create vaults, bounded by an explicit quota, without holding any authority over vaults it did not create. This is release 1 of a two-release plan; full design: docs/superpowers/specs/2026-09-03-self-service-vault-provisioning-design.md.

The problem this solves

Creating a vault (POST /vaults) or listing vaults (GET /vaults) has always required a global vaults:manage grant — the admin account role, or an access-policy allow with vault_id: NULL. That grant is far wider than "may create vaults": because a NULL-scoped allow matches every vault-scoped check, it also confers get/update/delete on every existing vault via CanManageVault, and role-assignment management everywhere via CanManageRoleAssignments — enough for its holder to award itself Key Vault Administrator in any vault on the instance. Handing an MSP's automation the only permission that let it create vaults also handed it the entire instance. There was no safe middle ground.

What a provisioning grant is

A provisioning grant (vault_provisioning_grants) is a bounded right: create up to quota vaults, and become full manager of what you create — vault- scoped vaults:manage plus a Key Vault Administrator role assignment on each vault, applied at creation time — and nothing else. It confers no authority over any vault the grantee did not create.

principal_id carries no foreign key to users and is not resolved by username alone: the grantee may be an OAuth2 service account (an oauth2_clients row, not a users row), which is how an MSP's automation typically authenticates.

Admin API and CLI

Instance-level routes, since a grant belongs to no vault:

text
PUT    /api/v1/vault-provisioning-grants/{principal_id}   issue, or re-quota an existing grant
DELETE /api/v1/vault-provisioning-grants/{principal_id}   revoke
GET    /api/v1/vault-provisioning-grants                  list every grant

PUT upserts: principal_id is UNIQUE, so a second PUT for the same principal changes its quota rather than creating a second grant (200 on a re-quota, 201 on a genuinely new grant).

CLI, under rocketvault vault-provisioning:

bash
# Issue a grant (a raw UUID is accepted and takes precedence over a
# username lookup -- needed for service-account principals)
rocketvault vault-provisioning grant alice --quota 5
rocketvault vault-provisioning grant 3b1e6c2a-9e4b-4f2d-8a2f-6b1c9d0e7f5a --quota 20

# List every grant
rocketvault vault-provisioning list

# Revoke a grant
rocketvault vault-provisioning revoke alice

Both the API and the CLI gate every operation on the global admin account role. This tier is admin-only and deliberately non-delegable — unlike role assignments, where Key Vault Data Access Administrator may delegate within an allow-list, there is no access-policy or role-assignment path here at all. A principal able to amend grants could raise its own quota, and the bound the grant exists to impose would be decorative. Every issue and revoke is audit-logged, as is every quota-denied create attempt.

Quota counts soft-deleted vaults — only a purge frees a slot

The quota check counts every row still present in vaults with created_by = <principal>, including soft-deleted ones. A soft-deleted vault still holds its name and is recoverable, so excluding it would let a grantee cycle delete-and-create past its bound indefinitely. A slot is freed only when the vault is purged — which happens automatically once it passes retention_days (the existing soft-delete purge scheduler), or immediately if an operator purges it by hand. Pre-existing vaults a principal already created count retroactively, since the count is by created_by, not by grant issue date — size quotas accordingly.

The check itself runs inside the vault-creation transaction, not the HTTP handler and not the repository: a check outside the transaction would race concurrent creates and let two requests both pass a quota of N-1 remaining and both succeed.

Grantees cannot set purge_protection

purge_protection is refused outright on a quota-bounded create (ErrPurgeProtectionNotPermitted). Allowing it would let a grantee protect a vault, soft-delete it, and pin its quota slot permanently — PurgeVault refuses to purge a protected vault, so an operator would have to intervene to unstick it. Grantees keep every other management capability over vaults they created; this restriction is the one exception, and it is admin-only on the provisioned path specifically.

One related, non-obvious consequence: the creator's automatic Key Vault Administrator role assignment does not include the purge data action (Microsoft.KeyVault/vaults/purge/action — only Key Vault Purge Operator carries that, plus the global admin role). A grantee can soft-delete and recover its own vault, but freeing a quota slot by purging it requires an admin, or a separate Key Vault Purge Operator grant in that vault.

Revocation is not a cascade

Revoking a grant (DELETE /vault-provisioning-grants/{principal_id} or rocketvault vault-provisioning revoke) stops the principal from creating any further vaults under that grant. It does not touch the vaults the principal already created, or that principal's vaults:manage/Key Vault Administrator rights over them. Cascading revocation would let one DELETE strip a customer's access to vaults it already has and depends on; removing that access, if ever wanted, is a deliberately separate operator action.

A related trap: a creator's two rights over its own vault — the vault-scoped vaults:manage access policy and the Key Vault Administrator role assignment, both written at creation time — are independent of each other. Running vault-access revoke against the creator removes only the role assignment, the data-plane half. The creator still holds vault-scoped vaults:manage, which alone satisfies CanManageRoleAssignments for that vault, so it can immediately re-grant itself Key Vault Administrator (or any other role) and be back where it started. Fully locking out a creator means deleting the underlying access_policies row, and there is no CLI for access policies at all — it is an HTTP-only, admin-only operation. An operator who runs vault-access revoke and assumes the creator is now locked out of the vault is wrong.

Known limitation: CLI secret writes ignore a creator's vault-scoped role

cmd/secrets/create.go, update.go, delete.go, import.go, and export.go each run a legacy global-role gate (admin or secrets_manager account role) ahead of the real, vault-scoped authorization check, as an AND. A provisioning grant's creator holds neither global role by default — only the vault-scoped Key Vault Administrator assignment created for it — so all five CLI secret-write commands refuse it, even though the identical write over the HTTP API succeeds for the same principal against the same vault. secrets get/secrets list have no such gate and work over the CLI exactly as expected. This means the feature's headline end-to-end journey — provision a vault, then put a secret in it — does not work through the CLI today; it works over HTTP. See .claude/known-bugs.md § B57 for the full root-cause analysis and fix recipe. This is a pre-existing defect, not introduced by this release, and it fails closed: it blocks a legitimate write, it does not permit an unauthorized one.

Fixed en route: PurgeVault orphaned role_assignments

Purging a vault already cleaned up its access_policies and vault_webhook_configs rows explicitly, but not role_assignments — the declared ON DELETE CASCADE on role_assignments.vault_id is inert on SQLite, where foreign_keys is off by default. This leaked occasionally before; now that every provisioned vault carries a creator role assignment, it would have leaked on every purge of a provisioned vault. PurgeVault now calls the new roleAssignmentRepository.DeleteByVault alongside the existing two cleanups, so no orphan row survives a purge.

Forward notice: a following release narrows global vaults:manage

Nothing in this release changes what a global vaults:manage grant does today — that grant still confers get/update/delete on every vault and role-assignment management everywhere, exactly as before. A following release (release 2 of this design, not part of this one) will narrow it to create-and-list only, removing both of those behaviours from its holders. CheckVaultScopedAccess (a NULL-scoped deny still matches; a NULL-scoped allow no longer does) and the corresponding changes to CanManageVault and CanManageRoleAssignments are the mechanism, but they are not shipped here.

Before upgrading to that release, find every principal who will be affected: a startup diagnostic added in this release, warnGlobalVaultManageGrants (internal/db/db.go), logs a warning naming every principal holding a NULL-scoped (vaults, manage, allow) policy on every server start. Run your instance at least once on this release and check its logs before upgrading further — the affected population should be small, since such policies are only ever created by hand through the admin-only createAccessPolicy endpoint.

Open question, not resolved by this release: a global vaults:manage holder who creates a vault today receives none of the per-vault creator grants a provisioning-grant holder gets (VaultService.CreateVault, the unbounded path, writes no access_policies or role_assignments row for the creator). That is harmless right now, because a global grant already confers authority over every vault including the one just created. It stops being harmless once the narrowing above ships: such a holder would create a vault it can no longer manage afterward. Whether and how to address this is left to release 2's planning — it is not decided here.

Upgrade steps

  1. No manual database migration step is required. migrateSchema creates vault_provisioning_grants idempotently on first startup after upgrading, in both the CREATE TABLE block and the migration path.
  2. Nothing existing changes behavior: this release is purely additive. A global vaults:manage holder keeps working exactly as before.
  3. If you operate as an MSP or hosting provider provisioning vaults on customers' behalf today, consider replacing that global grant with a bounded provisioning grant per customer principal — rocketvault vault-provisioning grant <principal> --quota <n>.
  4. Watch your startup logs for warnGlobalVaultManageGrants warnings ahead of the narrowing release, and start planning the migration of any principal it names.
