It found ~64% parity at the time, with a long list of fixed and still-open findings. This new audit supersedes it as the current parity snapshot but treats its "still open" items as a checklist to verify.

## Continuity vs the 2026-05-27 audit

The 2026-05-27 predecessor (`docs/plans/2026-05-23-azure-keyvault-parity-audit.md`) reported ~64% parity and a long "Remaining open items" list. Comparing that list against this audit's independent findings, three months later:

**Confirmed still open, independently re-found by this audit:**
- API wire-format divergence (name vs UUID addressing, flat vs `{value,nextLink}` envelopes, `{error:{code,message}}` shape) — predecessor's #2 "single largest outstanding fork," this audit's API-compatibility Medium findings (error shape, and see below).
- `VersionMiddleware`/`api/versioning.go` unwired — predecessor listed as "Low, dead code, wire or remove"; **this audit found it is still unwired three months later, and additionally found its hardcoded `v1` sunset date (2025-12-31) is now in the past** — escalated to High here because the code's existence actively misrepresents a capability that doesn't run.
- `SetPurgeProtection` has no HTTP/CLI surface — predecessor's Medium #4; this audit confirms it is **still** true for keys and certificates, and additionally found it's true for secrets too, and that vault-level purge protection does not cascade to protect contained items — escalated to High here given the security implication (a "purge-protected" vault offers no actual item-level protection).
- Retry-After header missing on 429 — predecessor Medium; still true.
- Tags as `[]string` not `map[string]string` — predecessor Low; still true.
- Certificate X.509 SAN/EKU/key_usage hardcoded — predecessor Medium; not independently re-verified in this pass (out of this audit's certificate-capability list) but no evidence found it changed.
- 409 Conflict never used, duplicate names 500 — predecessor implicitly covered under "error envelope"; this audit found and named it explicitly across all three resource types.

**Fixed since 2026-05-27 (predecessor listed as open, this audit confirms resolved):**
- Certificate policy CRUD, lifecycle attributes (enabled/exp/nbf) on all three resource types, true key versioning/rotation, per-item backup/restore for all three types, `HealthHandler`/`/health/database` wiring, `audit_logs` table now written — all confirmed still working in this audit (though several now have new caveats found independently, e.g. the health/readiness DB-ping gap below).
- Key sign/verify/encrypt/decrypt HTTP routes, PS*/ES256K/HS*/RSA1_5/AES-KW/AES-CBC algorithm coverage — confirmed solid.
- Session revocation, admin-guard on service-account creation — not re-tested directly in this pass but no contrary evidence found; access-control category scored strongly overall (84.8%).

**New since 2026-05-27 (did not exist or wasn't scoped in the predecessor):**
- Entire multi-vault + Azure-RBAC-role-parity architecture (11 built-in roles, vault-scoped role assignments) — a major addition, now the strongest-scoring category.
- Key rotation-policy scheduled execution (genuinely wired, not just CRUD) — confirmed real and tested.
- Certificate auto-renewal scheduler — confirmed real and tested, but with a newly-found config-surface bug (policy-API renewal settings are silently ignored by the scheduler).
- Hash-chained tamper-evident audit log — confirmed real, with a newly-found chain-continuity bug during retention purges.
- **New security-relevant findings not present in the predecessor**: CLI `vaults get`/`vaults list` authorization bypass (F2), Data Access Administrator privilege-escalation path (F1), `RestoreSecret` vault-ID mismatch, whole-vault restore's untested Postgres FK-ordering risk, SOC2 report's silent auth-outcome miscounting, role-assignment grant/revoke audit blind spot.

**Net read:** RocketVault has grown substantially in scope (multi-vault, RBAC, rotation, HSM) since May, and the predecessor's "wire-format compatibility" gap remains the single largest deliberate, known, unaddressed decision. But this audit surfaces a materially larger set of *new*, previously-undocumented correctness and security findings than the predecessor had open — most of them not wire-format cosmetics but real behavioral bugs (dead purge protection, audit blind spots on destructive operations, an unauthenticated CLI enumeration path, a compliance-report miscount). Parity computed here (57.8%/61.6%) is lower than the predecessor's informal "64%" not because RocketVault regressed, but because this audit scored more granularly, verified more rigorously (tests + Azure docs + direct code read rather than presence-checking), and covered categories the predecessor's rough count didn't cleanly separate (e.g., Access Control's role-by-role `dataAction` verification).

### What was fixed

**Purge protection is now real, settable, and cascades (Critical Finding #2 — commits `1e24095` secrets, `986fc07` keys, `d9a6136` certificates).** This was the largest of the six and shipped as three parallel per-resource-type tasks with an identical shape. Each resource gained a `PurgeProtection *bool` field on its service-layer and HTTP create/update DTOs (`purge_protection` JSON, `nil` meaning "no explicit value", matching the pre-existing `Enabled *bool` convention) and a `--purge-protection` flag on its `create`/`update` CLI commands, gated by `cmd.Flags().Changed(...)` — so the flag the DB column and `SetPurgeProtection` method had always accepted is finally reachable by a caller. Enforcement was completed on the manual `DELETE .../purge` path (previously only the background auto-purge scheduler honored it, and secrets had no manual-path check at all), returning a shared sentinel from `internal/repositories/purge_protection_errors.go` (`ErrSecretPurgeProtected`/`ErrKeyPurgeProtected`/`ErrCertPurgeProtected`) that each `api/errors_*.go` maps to **403, not 500**. Finally, each service's `Purge*` now performs a vault-level cascade check through an optional `VaultRepository`: if the containing vault has purge protection enabled, the item purge is refused even when the item itself carries no flag — which closes the "vault-level protection doesn't protect contained items" half of Finding #2.

Two corrections to that work landed mid-implementation, both from code review rather than from the plan, and both changed the shipped behavior relative to what was originally designed:

- **`16c1fa8`** fixed a **pre-existing bug in the shared retry-wrapping layer** that the purge-protection work only exposed: the wrapper re-wrapped inner errors with `%v` instead of `%w`, severing the `errors.Is` chain. With `retry.database.enabled` true — **the default production configuration** — every one of the new purge-protection sentinels would have reached the handler unrecognizable and surfaced as **HTTP 500 rather than 403**. The fix is a one-verb change with repo-wide reach, and it applies to every sentinel that crosses that layer, not just these three.
- The same review found that the vault-cascade check as first written **failed open**: an error reading the containing vault let the purge proceed. It now **fails closed** — an unreadable vault blocks the purge. This is a deliberate departure from what this audit's own Finding #2 recommendation implicitly assumed, and the fail-closed shape was then carried into the keys and certificates commits (`986fc07`, `d9a6136`).

**A final whole-branch review (`68a52d8`) after all nine tasks landed found four more issues,** all fixed in that commit: an inaccurate code comment claiming the new Data Access Administrator restriction covered revoke as well as grant (it does not — see below); `RestoreSecret`/`RestoreKey`/`RestoreCertificate` silently dropping `purge_protection` across a backup/restore round-trip, because the repository `Create` calls do not write that column — each `Restore*` now re-applies the decoded entity's flag via `SetPurgeProtection` after create, so a backup taken while protected no longer restores unprotected; three sentinel error messages (and their hand-copied 403 literals in `api/errors_{secret,key,certificate}.go`) that read as item-only even when a vault-level cascade block was what actually triggered them; and keys'/certificates' fail-closed cascade tests being weaker than the secrets equivalent, now at parity.

**CLI authorization bypass (Critical Finding #1 / F2 — `93339d1`).** `cmd/vaults/get.go` and `cmd/vaults/list.go` now run the same checks their HTTP equivalents in `api/vault.go` do: the pre-existing `requireCanManageVault` for `get`, and a new `requireCanListVaults` (`cmd/vaults/authz.go`, checked against `uuid.Nil` since list has no single target vault, mirroring `listVaults`). `TestVaultsGet_ForbiddenWithoutGrant` and `TestVaultsList_ForbiddenWithoutGlobalGrant` pin it. This closes the third instance of the B11/B13 bug class — CLI commands bypassing the middleware chain and never reproducing its check.

**Restore wrote the blob's vault, not the caller's (Secrets findings, High — `c5bf97d`).** The audit named only `RestoreSecret`; `RestoreKey` and `RestoreCertificate` carried the identical bug. All three `ItemBackupService` methods now take a `vaultID` parameter — the vault resolved from the authorized request via `vaultIDFromRequest` in `api/backup_item.go` — and write that onto the restored item, never the `vault_id` embedded in the backup blob. A caller with restore permission in one vault can no longer plant an item into any vault a crafted blob names.

**Audit-logging blind spots (Critical Findings #6 and #7 — `62c4b7b`, `51d8bae`).** `RoleAssignmentService.AssignRole` and `RevokeAssignment` now emit success-path `LogAuditInfo` rows (`assign_role`, `revoke_role_assignment`); previously `AssignRole` logged only failures and `RevokeAssignment` logged nothing on any path, leaving the RBAC system's most security-sensitive operation without a forensic trail. Separately, all six `Recover*`/`Purge*` methods across secrets, keys, and certificates now log success, mirroring the `vault_service.go` pattern that was already correct — an irreversible purge of vault material no longer completes silently. Eight tests across the four service packages pin both.

**SOC2 auth-outcome miscounting (Critical Finding #8 — `4e50061`).** `authenticationService` gained an optional `AuditService` dependency, wired in `internal/container/service_container.go`. `AuthenticateUser`'s four failure branches and `issueSession`'s success path now route through `AuditService.RecordEvent` — populating `Outcome`, `ResourceType`, and `Source` — instead of the lossy legacy `LogAuditInfo` shim that left `Outcome` empty and made `GenerateSOC2Report` count every real login, success or failure, as a failure. Because local login and OIDC share `issueSession`, both paths are fixed by the one change. The replacement test exercises the real write path end-to-end and asserts a persisted outcome, rather than hand-seeding `Outcome` into the repository as the old test did — which is what had masked the bug.

**Data Access Administrator role-grant restriction (Access control finding F1 — `ccdcb3d`, plus `4b4d0d1`).** `AssignRoleInput` gained `CallerIsGlobalAdmin`, set by both call sites (`api/role_assignments.go`'s `createRoleAssignment` and `cmd/vault-access/grant.go`) from the same global-admin check `CanManageRoleAssignments` already performs. `AssignRole` now rejects any role outside the `nonAdminGrantableRoles` allow-list — which deliberately excludes `Key Vault Data Access Administrator`, `Key Vault Purge Operator`, and `Key Vault Certificate User` — with a new `ErrRoleNotGrantable` sentinel, unless the caller is a global admin. This matches Azure's real ABAC restriction on the role. A same-day code-review follow-up, `4b4d0d1`, fixed the handler failing to map that sentinel, so the rejection surfaced as **HTTP 500 instead of 403**. Note the scope precisely: **this restriction covers granting only, not revoking** — see the deferred item at the end of this section.

### New finding — not yet fixed: `PurgeVault`'s cascade-delete ignores per-item purge protection

**Severity: High. Status: open, deliberately not fixed in this branch.** Tracked as `.claude/known-bugs.md` § B22.

The final review of the purge-protection work found that `VaultService.PurgeVault` — the path behind `DELETE /api/v1/vaults/{vault_name}/purge` — cascades through `internal/services/vaults/cascade_adapter.go` into each resource repository's `PurgeVaultContents(ctx, vaultID)`, and those methods run an unconditional `DELETE FROM <table> WHERE vault_id = ?` **with no `purge_protection` predicate at all**. That was intentional when written (its own comment cites avoiding orphaned rows once the containing vault is gone), and it was **inert**: no caller could set `purge_protection` to `true` on any secret, key, or certificate, so a predicate that was never satisfied could not matter.

This branch made per-item purge protection real and settable for the first time. That converts a dormant design choice into **a live, reachable bypass of the exact guarantee the same branch just added to the single-item purge path**: a caller who purges an unprotected vault silently destroys every purge-protected item inside it — no error, no partial-failure signal, and no audit trail distinguishing it from an ordinary vault purge beyond the vault-purge event itself. This is the direct descendant of Critical Finding #2's core complaint, that "a 'purge-protected' vault offers no actual item-level protection"; it was only visible once the rest of #2 was fixed.

Two things bound the exposure, and neither removes it. Vault purge is already a high-privilege operation, gated on the `Key Vault Purge Operator` role or global admin, so the practical blast radius is narrower than the original findings — this is a **protection-bypass and data-loss** risk, not a privilege-escalation one. And the vault must itself be unprotected, since vault-level purge protection still blocks purging the vault. But an operator who sets `purge_protection` on an individual secret today receives a guarantee the system does not keep.

**It was deliberately left unfixed** because closing it changes `PurgeVault`'s existing contract and needs a decision before a patch. The two defensible directions:

1. **Protected items block the vault purge.** Add `AND purge_protection = FALSE` to the three `PurgeVaultContents` methods, and have `PurgeVault` refuse (or report partial completion) when protected rows remain — the caller must purge or wait out those items individually first. This is closest to Azure's "cannot purge while protected objects remain" semantics.
2. **Vault purge overrides item-level protection, by design.** Keep the current behavior, but state it explicitly in the API/CLI documentation, the parity doc, and the `--purge-protection` flag help text, so the guarantee is advertised as *within-vault* and nothing more.

Either is acceptable. What is not acceptable is the current state, where the code silently implements (2) while the newly-shipped feature reads to an operator as (1). The choice also implies a broader answer — whether per-item purge protection is meant to survive vault deletion at all — for which Azure has no exact analogue given RocketVault's multi-vault model, so it warrants its own scoped plan and review rather than a same-wave patch.

### Deferred — the Data Access Administrator restriction is grant-only

**Severity: Medium. Status: open, deliberate deferral, not urgent.** Tracked as `.claude/known-bugs.md` § B21.

`ccdcb3d`'s restriction is enforced in `AssignRole` only. `RevokeAssignment` carries no caller-authority signal in its signature and never consults `nonAdminGrantableRoles`, so a non-global-admin Data Access Administrator **can revoke** a `Key Vault Purge Operator`, `Key Vault Certificate User`, or another `Key Vault Data Access Administrator` assignment in their vault, even though they cannot grant one. Azure's real ABAC condition restricts both sides.

This is rated lower than the grant-side bug it descends from because the effect is tamper/denial rather than privilege escalation, and exploiting it requires already holding Data Access Administrator in that vault. The fix is small but not zero: `RevokeAssignment` needs the same `CallerIsGlobalAdmin`-style parameter `AssignRole` takes, set at its two call sites (`api/role_assignments.go`, `cmd/vault-access/grant.go`), then the same allow-list check applied to the assignment being revoked rather than the role being granted.

### Process note

This remediation was executed with the same subagent-driven method the appendix describes for the audit itself: nine independent implementation tasks, each reviewed on its own before commit, followed by a final review pass over the whole branch. Review is where the three extra commits came from — `4b4d0d1` and `16c1fa8` from per-task review, `68a52d8` from the whole-branch pass — and it is also where both gaps documented above were found. The `%v`-vs-`%w` retry-layer bug in particular would have shipped the headline purge-protection fix returning 500s in the default production configuration, and no task-scoped test would have caught it, because the defect lived outside every task's own boundary. ## Appendix: methodology

Eight independent subagents (Sonnet 5), one per weighted category, each: (1) used WebSearch/WebFetch to find and read current Microsoft Learn documentation for that category, recording exact behavior/limits/defaults with URLs; (2) traced RocketVault's actual implementation via direct code reads (not documentation), citing file paths and line numbers; (3) ran the relevant `go test` suites and recorded pass/fail counts; (4) scored every capability using the decision-flow rubric in `docs/plans/2026-05-23-azure-keyvault-parity-audit-template.md`, splitting a capability into multiple rows where it had multiple distinct behaviors; (5) treated `.claude/azure-keyvault-parity.md` and the 2026-05-23 draft template as leads only, explicitly flagging any place they were found stale or wrong. This controller then read all 8 category reports in full, recomputed the parity math directly from each report's table (several agents' self-reported score-distribution summaries had minor arithmetic inconsistencies with their own tables — this document's numbers are recomputed from the tables themselves, not copied from agent summaries), consolidated findings, and cross-checked continuity against the 2026-05-27 predecessor audit discovered during research.

All test runs were executed in a git worktree (`worktree-azure-parity-audit`) rebased onto the local `v-4.0.0` tip (commit `0934705`) to include the 12 locally-committed-but-unpushed rotation-scheduler commits. `go build ./...` and every referenced `go test` invocation passed cleanly at audit time; no test failures were found anywhere in the areas this audit traced — every `partial`/`missing` score reflects a real behavioral or architectural divergence found by direct code inspection and Azure-doc comparison, not a failing test.
