RocketVault Administrator Manual

The authoritative operational guide to every RocketVault feature — installation, identity, secrets, keys, certificates, governance, and integration.

1. Introduction & Mental Model

What it is

RocketVault is a self-hosted, open-source alternative to Azure Key Vault, written in Go. It manages secrets, RSA/ECDSA keys, and X.509 certificates through a REST API and a Cobra CLI, with JWT+TOTP authentication and RBAC. Azure Key Vault parity

The layers

Requests flow through a security gateway (auth, RBAC, rate limiting) into the REST API, then into a service container (business logic), down to pure repositories (data access), and finally SQLite (dev) or PostgreSQL (prod). The CLI calls the same service container directly. Secrets, keys, and certificates are encrypted at rest with AES-256-GCM.

See also: System Architecture (interactive)

2. Installation & First Run

What it is

RocketVault runs as a single Go binary. The server reads exactly one config file, .rocketvault.yaml, from the working directory or --config.

Admin operations

Run from source
go run main.go serve
go run main.go serve --config /path/custom.yaml
Verify it is up
export BASE=http://localhost:8774
curl -s $BASE/api/v1/health/live

Notes & troubleshooting

  • The server listens on :8774 by default (see server.listen_addr).
  • environment: development | production selects database pool defaults.

3. Bootstrap — First Admin User

What it is

A one-time bootstrap token creates the first admin without authentication. After use, the token is consumed. The response returns a TOTP secret you must register in an authenticator app — every login requires a TOTP code.

Admin operations

Bootstrap is a CLI-only operation — there is no HTTP endpoint. The command talks to the service container directly, validates the token, creates the admin, and then invalidates the token.

rocketvault users admin \
  --admin-username admin \
  --admin-password admin123 \
  --bootstrap-token <token>
Register the returned totp_qr_url before logging in. You can mint codes with oathtool --totp --base32 <secret>.

See also: Admin Setup Guide

5. Authentication

What it is

Login requires username + password + a TOTP code, and returns a short-lived JWT plus a refresh token. Sessions are tracked and individually revocable.

Admin operations

Login (API)
TOKEN=$(curl -s -X POST $BASE/api/v1/users/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123",
       "totp_code":"123456"}' | jq -r .token)
Sessions (API)
# Refresh
curl -X POST $BASE/api/v1/users/refresh \
  -d '{"refresh_token":"<rt>"}'
# List / revoke
curl $BASE/api/v1/users/sessions -H "Authorization: Bearer $TOKEN"
curl -X DELETE $BASE/api/v1/users/sessions/<id> -H "Authorization: Bearer $TOKEN"

Notes & troubleshooting

  • Auth endpoints are rate-limited (default 5 req/min) — see §21.
  • DELETE /api/v1/users/sessions revokes all sessions for the caller.

See also: Manual Testing §5

6. JWT Signing & Key Sources

What it is

JWTs are signed asymmetrically and verifiable via JWKS at /jwks.json. Three providers control where the signing key lives, set by jwt.key_source.

ProviderStorageAlgorithmRotation
os_store (default)OS keychain, PEM-file fallbackRS256No
self_pkiRocketVault's own encrypted DBES256Yes (runtime)
external_pkiPEM from file or env varRS256/ES256No

Admin operations

Inspect JWKS
curl -s $BASE/jwks.json | jq '.keys[0].alg'
Rotate (self_pki only)
curl -X POST $BASE/api/v1/jwks/rotate \
  -H "Authorization: Bearer $TOKEN"
# os_store returns 400 (rotation unsupported)
With os_store, the key is stored in the OS keychain (secret-tool lookup service rocketvault …) and never written to a world-readable path. Headless hosts fall back to ~/.local/share/rocketvault/jwt-signing.pem (mode 0600).

See also: Manual Testing §§6,15,16

7. User Management

What it is

Admins create, list, update, and delete users. Each user has a role (admin or user) and a TOTP secret issued at creation.

Admin operations

CLI
rocketvault users create --username alice --role user \
  --username admin --password admin123 --totp-code 123456
rocketvault users list --username admin --password admin123 --totp-code 123456
API
curl -X POST $BASE/api/v1/users -H "Authorization: Bearer $TOKEN" \
  -d '{"username":"alice","password":"alicepassword123","role":"user"}'
curl -X PUT $BASE/api/v1/users/<id> -H "Authorization: Bearer $TOKEN" \
  -d '{"role":"admin"}'

Notes & troubleshooting

  • Create/list/update/delete require the admin role.

See also: Manual Testing §7

8. RBAC & Access Policies

What it is

Two complementary controls: roles (admin vs user) gate broad operations, and access policies grant a specific principal (user or service account) access to a specific resource. A policy binds a principal to a resource type/id and a set of allowed actions.

Admin operations

Create a policy
curl -X POST $BASE/api/v1/access-policies \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"read-db-secret","principal_id":"<id>",
       "resource_type":"secret","resource_id":"<id>",
       "actions":["read"]}'
Inspect
curl $BASE/api/v1/access-policies -H "Authorization: Bearer $TOKEN"
curl $BASE/api/v1/access-policies/principal/<id> \
  -H "Authorization: Bearer $TOKEN"

See also: Manual Testing §13

9. OAuth2 Service Accounts

What it is

A service account is a machine identity (Azure KV service-principal equivalent) that authenticates via the OAuth2 client-credentials flow — no TOTP. Service accounts are read-only consumers: they retrieve secrets/keys/certs an admin stored and granted them, never create or manage.

When to use it

CI/CD pipelines, applications fetching their own config at runtime, service-to-service secret sharing, scheduled jobs — any non-human caller.

Admin operations

Create + token
SA=$(curl -s -X POST $BASE/api/v1/service-accounts \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"ci-pipeline"}')
# client_secret is shown ONCE
curl -X POST $BASE/api/v1/oauth2/token \
  -u "ci-pipeline:$SECRET" -d "grant_type=client_credentials"
Rotate / delete
curl -X POST $BASE/api/v1/service-accounts/<id>/rotate \
  -H "Authorization: Bearer $TOKEN"
curl -X DELETE $BASE/api/v1/service-accounts/<id> \
  -H "Authorization: Bearer $TOKEN"
The client_id is the service-account name, not its UUID. Deleting or rotating immediately invalidates live tokens.

See also: Consuming Secrets Guide, Manual Testing §14
