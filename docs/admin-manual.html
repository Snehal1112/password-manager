RocketVault Administrator Manual

The authoritative operational guide to every RocketVault feature — installation, identity, secrets, keys, certificates, governance, and integration.

1. Introduction & Mental Model

What it is

RocketVault is a self-hosted, open-source alternative to Azure Key Vault, written in Go. It manages secrets, RSA/ECDSA keys, and X.509 certificates through a REST API and a Cobra CLI, with JWT+TOTP authentication and RBAC. Azure Key Vault parity

The layers

Requests flow through a security gateway (auth, RBAC, rate limiting) into the REST API, then into a service container (business logic), down to pure repositories (data access), and finally SQLite (dev) or PostgreSQL (prod). The CLI calls the same service container directly. Secrets, keys, and certificates are encrypted at rest with AES-256-GCM.

See also: System Architecture (interactive)

2. Installation & First Run

What it is

RocketVault runs as a single Go binary. The server reads exactly one config file, .rocketvault.yaml, from the working directory or --config.

Admin operations

Run from source
go run main.go serve
go run main.go serve --config /path/custom.yaml
Verify it is up
export BASE=http://localhost:8774
curl -s $BASE/api/v1/health/live

Notes & troubleshooting

  • The server listens on :8774 by default (see server.listen_addr).
  • environment: development | production selects database pool defaults.

See also: Setup Guide

3. Bootstrap — First Admin User

What it is

A one-time bootstrap token creates the first admin without authentication. After use, the token is consumed. The response returns a TOTP secret you must register in an authenticator app — every login requires a TOTP code.

Admin operations

Bootstrap is a CLI-only operation — there is no HTTP endpoint. The command talks to the service container directly, validates the token, creates the admin, and then invalidates the token.

rocketvault users admin \
  --admin-username admin \
  --admin-password admin123 \
  --bootstrap-token <token>
Register the returned totp_qr_url before logging in. You can mint codes with oathtool --totp --base32 <secret>.

See also: Admin Setup Guide

5. Authentication

What it is

Login requires username + password + a TOTP code, and returns a short-lived JWT plus a refresh token. Sessions are tracked and individually revocable.

Admin operations

Login (API)
TOKEN=$(curl -s -X POST $BASE/api/v1/users/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123",
       "totp_code":"123456"}' | jq -r .token)
Sessions (API)
# Refresh
curl -X POST $BASE/api/v1/users/refresh \
  -d '{"refresh_token":"<rt>"}'
# List / revoke
curl $BASE/api/v1/users/sessions -H "Authorization: Bearer $TOKEN"
curl -X DELETE $BASE/api/v1/users/sessions/<id> -H "Authorization: Bearer $TOKEN"

Notes & troubleshooting

  • Auth endpoints are rate-limited (default 5 req/min) — see §21.
  • DELETE /api/v1/users/sessions revokes all sessions for the caller.

See also: Manual Testing §5

6. JWT Signing & Key Sources

What it is

JWTs are signed asymmetrically and verifiable via JWKS at /jwks.json. Three providers control where the signing key lives, set by jwt.key_source.

ProviderStorageAlgorithmRotation
os_store (default)OS keychain, PEM-file fallbackRS256No
self_pkiRocketVault's own encrypted DBES256Yes (runtime)
external_pkiPEM from file or env varRS256/ES256No

Admin operations

Inspect JWKS
curl -s $BASE/jwks.json | jq '.keys[0].alg'
Rotate (self_pki only)
curl -X POST $BASE/api/v1/jwks/rotate \
  -H "Authorization: Bearer $TOKEN"
# os_store returns 400 (rotation unsupported)
With os_store, the key is stored in the OS keychain (secret-tool lookup service rocketvault …) and never written to a world-readable path. Headless hosts fall back to ~/.local/share/rocketvault/jwt-signing.pem (mode 0600).

See also: Manual Testing §§6,15,16

7. User Management

What it is

Admins create, list, update, and delete users. Each user has a role (admin or user) and a TOTP secret issued at creation.

Admin operations

CLI
rocketvault users create --username alice --role user \
  --username admin --password admin123 --totp-code 123456
rocketvault users list --username admin --password admin123 --totp-code 123456
API
curl -X POST $BASE/api/v1/users -H "Authorization: Bearer $TOKEN" \
  -d '{"username":"alice","password":"alicepassword123","role":"user"}'
curl -X PUT $BASE/api/v1/users/<id> -H "Authorization: Bearer $TOKEN" \
  -d '{"role":"admin"}'

Notes & troubleshooting

  • Create/list/update/delete require the admin role.

See also: Manual Testing §7

8. RBAC & Access Policies

What it is

Two complementary controls: roles (admin vs user) gate broad operations, and access policies grant a specific principal (user or service account) access to a specific resource. A policy binds a principal to a resource type/id and a set of allowed actions.

Admin operations

Create a policy
curl -X POST $BASE/api/v1/access-policies \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"read-db-secret","principal_id":"<id>",
       "resource_type":"secret","resource_id":"<id>",
       "actions":["read"]}'
Inspect
curl $BASE/api/v1/access-policies -H "Authorization: Bearer $TOKEN"
curl $BASE/api/v1/access-policies/principal/<id> \
  -H "Authorization: Bearer $TOKEN"

See also: Manual Testing §13

9. OAuth2 Service Accounts

What it is

A service account is a machine identity (Azure KV service-principal equivalent) that authenticates via the OAuth2 client-credentials flow — no TOTP. Service accounts are read-only consumers: they retrieve secrets/keys/certs an admin stored and granted them, never create or manage.

When to use it

CI/CD pipelines, applications fetching their own config at runtime, service-to-service secret sharing, scheduled jobs — any non-human caller.

Admin operations

Create + token
SA=$(curl -s -X POST $BASE/api/v1/service-accounts \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"ci-pipeline"}')
# client_secret is shown ONCE
curl -X POST $BASE/api/v1/oauth2/token \
  -u "ci-pipeline:$SECRET" -d "grant_type=client_credentials"
Rotate / delete
curl -X POST $BASE/api/v1/service-accounts/<id>/rotate \
  -H "Authorization: Bearer $TOKEN"
curl -X DELETE $BASE/api/v1/service-accounts/<id> \
  -H "Authorization: Bearer $TOKEN"
The client_id is the service-account name, not its UUID. Deleting or rotating immediately invalidates live tokens.

See also: Consuming Secrets Guide, Manual Testing §14

10. Secrets

What it is

Encrypted-at-rest key/value secrets (AES-256-GCM). Only the owner or an admin can read a secret via the flat routes. Secrets support tags, generation, and import/export.

Admin operations

CLI
rocketvault secrets create --name db-password --value s3cret \
  --username admin --password admin123 --totp-code 123456
rocketvault secrets list  --username admin --password admin123 --totp-code 123456
API
curl -X POST $BASE/api/v1/secrets -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"db-password","value":"s3cret","tags":["database"]}'
curl -X POST $BASE/api/v1/secrets/generate -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"api-key","length":32,"type":"alphanumeric"}'

Notes & troubleshooting

  • Updating a secret's value creates a new version (see §11).
  • Export/import: POST /secrets/export, POST /secrets/import.

See also: Manual Testing §8

11. Secret Versions

What it is

Every value update creates a new, retained version. Old versions stay readable.

Admin operations

List / get (API)
curl $BASE/api/v1/secrets/<id>/versions -H "Authorization: Bearer $TOKEN"
curl $BASE/api/v1/secrets/<id>/versions/1 -H "Authorization: Bearer $TOKEN"
curl $BASE/api/v1/secrets/<id>/versions/latest -H "Authorization: Bearer $TOKEN"
CLI
rocketvault version list   <secret-id> --username admin --password admin123 --totp-code 123456
rocketvault version latest <secret-id> --username admin --password admin123 --totp-code 123456

See also: Manual Testing §9

12. Secret Rotation

What it is

Rotation policies define how often a secret should rotate, with reminder windows and optional auto-rotate. History is tracked, and due rotations can be queried. Managed primarily through the CLI.

Admin operations

Manage policies
rocketvault secrets rotation create --secret-id <id> --interval 30d \
  --username admin --password admin123 --totp-code 123456
rocketvault secrets rotation list   --username admin --password admin123 --totp-code 123456
Operate
rocketvault secrets rotation rotate  --secret-id <id> ...
rocketvault secrets rotation history --secret-id <id> ...
rocketvault secrets rotation status  ...

See also: Integration Examples — rotation

13. Keys

What it is

RSA and ECDSA private keys, encrypted at rest, with cryptographic operations (wrap/unwrap, sign/verify, encrypt/decrypt), rotation, and version history.

Admin operations

Create
# RSA: bits = 2048 | 3072 | 4096
curl -X POST $BASE/api/v1/keys -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"my-rsa-key","type":"RSA","bits":2048}'
# ECDSA: curve = P-256 | P-384 | P-521
curl -X POST $BASE/api/v1/keys -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"my-ec-key","type":"ECDSA","curve":"P-256"}'
Operate
curl -X POST $BASE/api/v1/keys/<id>/rotate  -H "Authorization: Bearer $TOKEN"
curl -X POST $BASE/api/v1/keys/<id>/wrap    -H "Authorization: Bearer $TOKEN" -d '{"plaintext":"..."}'
curl -X POST $BASE/api/v1/keys/<id>/sign    -H "Authorization: Bearer $TOKEN" -d '{"value":"aGVsbG8=","algorithm":"RS256"}'
Use bits for RSA and curve for ECDSA — the earlier docs sometimes omitted bits.

See also: Manual Testing §10

14. Certificates & Certificate Policies

What it is

Self-signed X.509 certificate lifecycle management. Each certificate may carry a policy describing auto-renewal (validity, key type/curve, SANs, issuer) used by the renewal scan.

Admin operations

Create + policy
curl -X POST $BASE/api/v1/certificates -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"my-tls-cert","common_name":"example.com",
       "validity_days":365,"key_type":"RSA","key_size":2048}'
curl -X PUT $BASE/api/v1/certificates/<id>/policy -H "Authorization: Bearer $TOKEN" \
  -d '{"auto_renew":true,"days_before_expiry":30}'
CLI
rocketvault certificate list  --username admin --password admin123 --totp-code 123456
rocketvault certificate renew <id> --username admin --password admin123 --totp-code 123456

See also: Manual Testing §11

15. Multi-Vault

What it is

Resources live in named vaults (Azure KV parity). A built-in default vault holds everything created via the flat routes. Vault names are 3–63 lowercase alphanumerics/hyphens, no leading/trailing hyphen.

Visibility model

Route familyExampleVisibility
FlatGET /api/v1/secretsPer-user (owner only)
Vault-scopedGET /api/v1/vaults/{name}/secretsMembers see all

Admin operations

Manage vaults (admin)
curl -X POST  $BASE/api/v1/vaults -H "Authorization: Bearer $TOKEN" -d '{"name":"team-alpha"}'
curl -X PATCH $BASE/api/v1/vaults/team-alpha -H "Authorization: Bearer $TOKEN" -d '{"retention_days":7}'
curl -X DELETE $BASE/api/v1/vaults/team-alpha -H "Authorization: Bearer $TOKEN"  # 204; refuses 'default'
CLI
rocketvault vaults create  team-alpha ...
rocketvault vaults recover team-alpha ...
rocketvault vaults purge   team-alpha ...
Vault management requires the vaults:manage permission (admin only). The default vault cannot be deleted.

See also: Manual Testing §12.5

16. Soft-Delete, Restore & Purge

What it is

Secrets, keys, and certificates are soft-deleted (retained, default 30 days) and can be restored or permanently purged. Purge protection can block permanent deletion.

Admin operations

Flat (per-user)
curl $BASE/api/v1/deleted/secrets -H "Authorization: Bearer $TOKEN"
curl -X POST   $BASE/api/v1/deleted/secrets/<id>/restore -H "Authorization: Bearer $TOKEN"
curl -X DELETE $BASE/api/v1/deleted/secrets/<id>/purge   -H "Authorization: Bearer $TOKEN"
Vault-scoped (by membership)
curl $BASE/api/v1/vaults/default/deleted/secrets -H "Authorization: Bearer $TOKEN"
curl -X POST $BASE/api/v1/vaults/default/deleted/secrets/<id>/restore -H "Authorization: Bearer $TOKEN"
Key/certificate restore/purge are exposed only on the flat /deleted/keys/… and /deleted/certificates/… routes.

See also: Manual Testing §12

17. Audit Logs & Compliance

What it is

Every security-relevant action is recorded in a hash-chained audit log (tamper-evident). Logs are queryable with filters, and SOC 2 / GDPR reports can be generated. Admin only.

Admin operations

Query + reports (API)
curl "$BASE/api/v1/audit/logs?action=login&limit=50" -H "Authorization: Bearer $TOKEN"
curl "$BASE/api/v1/audit/reports/soc2?start_date=2026-01-01&end_date=2026-06-01" -H "Authorization: Bearer $TOKEN"
curl "$BASE/api/v1/audit/reports/gdpr?subject_id=<id>" -H "Authorization: Bearer $TOKEN"
Retention config
curl  $BASE/api/v1/audit/config -H "Authorization: Bearer $TOKEN"
curl -X PATCH $BASE/api/v1/audit/config -H "Authorization: Bearer $TOKEN" \
  -d '{"retention_days":365}'
The logs response includes an integrity_ok flag — the result of verifying the hash chain.

See also: Manual Testing

18. Backup & Restore

What it is

Two levels: full database backups via the CLI, and per-item encrypted backup/restore blobs for individual secrets, keys, and certificates via the API.

Admin operations

Full backup (CLI)
rocketvault backup create  --username admin --password admin123 --totp-code 123456
rocketvault backup list    --username admin --password admin123 --totp-code 123456
rocketvault backup restore --file /path/backup.json ...
Per-item (API)
curl -X POST $BASE/api/v1/secrets/<id>/backup -H "Authorization: Bearer $TOKEN"
curl -X POST $BASE/api/v1/secrets/restore    -H "Authorization: Bearer $TOKEN" -d '{...blob...}'

See also: Integration Examples — backup

19. HSM / PKCS#11

What it is

RocketVault can store and operate keys on a PKCS#11 token (hardware HSM, or SoftHSM2 for testing). Enable via the hsm config block; keys are stored as pkcs11:<uuid> instead of an encrypted PEM blob.

Configuration

hsm:
  enabled: true
  lib_path: /usr/lib/softhsm/libsofthsm2.so
  token_label: rocketvault
  pin: "1234"
  slot_id: 0

Supported algorithms

OperationAlgorithms
Sign / VerifyRS256/384/512, PS256/384/512, ES256/384/512
Encrypt / DecryptRSA-OAEP (SHA-1), RSA-OAEP-256 (SHA-256)
Key generationRSA 2048/4096, ECDSA P-256/384/521
Look for PKCS#11 HSM key provider initialised in the logs. P-256K (secp256k1) always uses the software provider.

See also: SoftHSM2 Testing Guide

21. Rate Limiting

What it is

Per-IP rate limits protect the API. Auth endpoints have a tighter limit than general endpoints.

Endpoint groupDefault (dev)
All API endpoints300 req/min
Auth (/login, /refresh, /oauth2/token)5 req/min
Tune via the rate_limit.default and rate_limit.auth config keys. Exceeding a limit returns 429 Too Many Requests.

See also: Manual Testing §17

22. Performance Internals

What it is

Two tunable subsystems run transparently. Caching: an in-memory key cache (key_cache.*, default 60s TTL / 500 entries) and a secret cache speed up reads. Retry: database and external-service operations use exponential backoff with jitter and a circuit breaker (retry.*).

These are configuration-tuned rather than operated directly — defaults are production-safe. Adjust only with measurement. The key_cache and retry blocks in §4 Configuration list the tunable keys.

See also: System Architecture (caching, retry, and circuit-breaker internals are shown in the service-layer diagram)

23. Database Migrations

What it is

Schema migrations run at startup, and a CLI provides explicit control: status, targeted migration, and authoring new migration files.

Admin operations

rocketvault migrate              # apply all pending
rocketvault migrate:status       # show applied / pending
rocketvault migrate:to <version> # migrate to a specific version
rocketvault migrate:create <desc># scaffold a new migration file
Each migration is recorded in schema_migrations and applied exactly once.

25. Consuming Secrets in Your Application

What it is

Applications retrieve secrets at runtime using a service-account OAuth2 token, so secrets never live in code or config. Three integration styles are supported.

Options

Go (vaultclient)
client, _ := vaultclient.New(vaultclient.Config{
  URL:          "http://localhost:8774",
  ClientID:     "my-app",                 // SA name
  ClientSecret: os.Getenv("VAULT_CLIENT_SECRET"),
  Secrets: []vaultclient.SecretMapping{
    {Name:"DB_PASSWORD", UUID:"<uuid>"}},
})
secrets, _ := client.GetMany(ctx, []string{"DB_PASSWORD"})
Shell / direct HTTP
# Get token
curl -X POST $BASE/api/v1/oauth2/token \
  -d "grant_type=client_credentials&client_id=my-app&client_secret=$SEC"
# Fetch a secret by UUID
curl $BASE/api/v1/secrets/<uuid> -H "Authorization: Bearer <access_token>"
VAULT_CLIENT_SECRET must come from an environment variable, never a config file. The server's own vault_client.client_id must be empty.

See also: Consuming Secrets Guide

26. CI/CD Integration

What it is

Pipelines authenticate with a service account (or admin credentials stored as CI secrets) to back up, validate, or fetch secrets during builds and deploys.

Pattern

# GitHub Actions / Jenkins — fetch a token, then call the API
TOKEN=$(curl -s -X POST $API_URL/oauth2/token \
  -d "grant_type=client_credentials&client_id=$CI_SA&client_secret=$CI_SECRET" | jq -r .access_token)
curl -s $API_URL/secrets/<uuid> -H "Authorization: Bearer $TOKEN" | jq -r .value

Appendix D — Security Checklist

  • VAULT_CLIENT_SECRET in env vars only — never a config file or git.
  • Server's vault_client.client_id is empty (the server must not call itself).
  • Each application has its own least-privilege service account.
  • Rotate service-account secrets periodically (/service-accounts/{id}/rotate).
  • JWT signing key persists across restarts (keychain or 0600 PEM) — never in /etc/ssl/certs.
  • Audit retention configured; verify integrity_ok on audit queries.
  • Purge protection enabled for sensitive vaults.

See also: Security Notes
