RocketVault Administrator Manual

The authoritative operational guide to every RocketVault feature — installation, identity, secrets, keys, certificates, governance, and integration.

RocketVault · self-hosted Azure Key Vault alternative · Go · API /api/v1 · Last updated 2026-06-03

0. Before You Begin

Prerequisites

  • Go 1.24+ to build and run the server (go run main.go serve).
  • curl and jq for the API examples; oathtool to mint TOTP codes without a phone.
  • A populated .rocketvault.yaml (the only config the server reads). Key settings: server.listen_addr (default :8774), the bootstrap token, and jwt.*.
  • The server running and an admin bootstrapped (see Quick Start).

Conventions in this manual

  • $BASE is http://localhost:8774; $TOKEN is an admin JWT from login.
  • Example responses are captured from a live server; secret values, key material, and tokens are shown as <redacted> placeholders.
  • Each operation shows tabs — cURL, CLI, and a real Response where applicable.

Quick Start — End to End

This walkthrough goes from a fresh server to an application reading a secret. Every command is copy-pasteable; responses are real (redacted).

1. Start the server

go run main.go serve
export BASE=http://localhost:8774
curl -s $BASE/api/v1/health/live      # {"status":"OK"}

2. Bootstrap the first admin (CLI only)

go run main.go users admin \
  --admin-username admin --admin-password admin123 \
  --bootstrap-token <your-bootstrap-token>
# stdout includes:  TOTP Secret: otpauth://...&secret=<BASE32>
Register the otpauth:// URL in an authenticator app, or mint codes with oathtool --totp --base32 <BASE32>. Every login needs a TOTP code.

3. Log in

TOKEN=$(curl -s -X POST $BASE/api/v1/users/login -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123","totp_code":"'"$(oathtool --totp --base32 <BASE32>)"'"}' \
  | jq -r .token)

4. Store a secret

curl -s -X POST $BASE/api/v1/secrets -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"DB_PASSWORD","value":"s3cret"}' | jq .id   # save this UUID

5. Create a service account and grant it read access

SA=$(curl -s -X POST $BASE/api/v1/service-accounts -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"my-app"}')                 # client_secret shown ONCE
SECRET=$(echo "$SA" | jq -r .client_secret); SA_ID=$(echo "$SA" | jq -r .id)
curl -s -X POST $BASE/api/v1/access-policies -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"app-read","principal_id":"'"$SA_ID"'","resource_type":"secret","resource_id":"<secret-uuid>","actions":["read"]}'

6. Consume the secret as the application

APP_TOKEN=$(curl -s -X POST $BASE/api/v1/oauth2/token \
  -u "my-app:$SECRET" -d "grant_type=client_credentials" | jq -r .access_token)
curl -s $BASE/api/v1/secrets/<secret-uuid> -H "Authorization: Bearer $APP_TOKEN" | jq .value

Each step is detailed in its own section below.

1. Introduction & Mental Model

What it is

RocketVault is a self-hosted, open-source alternative to Azure Key Vault, written in Go. It manages secrets, RSA/ECDSA keys, and X.509 certificates through a REST API and a Cobra CLI, with JWT+TOTP authentication and RBAC. Azure Key Vault parity

The layers

Requests flow through a security gateway (auth, RBAC, rate limiting) into the REST API, then into a service container (business logic), down to pure repositories (data access), and finally SQLite (dev) or PostgreSQL (prod). The CLI calls the same service container directly. Secrets, keys, and certificates are encrypted at rest with AES-256-GCM.

See also: System Architecture (interactive)

2. Installation & First Run

What it is

RocketVault runs as a single Go binary. The server reads exactly one config file, .rocketvault.yaml, from the working directory or --config.

Admin operations

Run from source
go run main.go serve
go run main.go serve --config /path/custom.yaml
Verify it is up
export BASE=http://localhost:8774
curl -s $BASE/api/v1/health/live

Notes & troubleshooting

  • The server listens on :8774 by default (see server.listen_addr).
  • environment: development | production selects database pool defaults.

See also: Setup Guide

3. Bootstrap — First Admin User

What it is

A one-time bootstrap token creates the first admin without authentication. After use, the token is consumed. The response returns a TOTP secret you must register in an authenticator app — every login requires a TOTP code.

Admin operations

Bootstrap is a CLI-only operation — there is no HTTP endpoint. The command talks to the service container directly, validates the token, creates the admin, and then invalidates the token.

rocketvault users admin \
  --admin-username admin \
  --admin-password admin123 \
  --bootstrap-token <token>
Register the returned totp_qr_url before logging in. You can mint codes with oathtool --totp --base32 <secret>.

See also: Admin Setup Guide

What it is

All runtime behavior is driven by .rocketvault.yaml. The top-level sections below are read by the server at startup.

jwtkey_source (os_store/self_pki/external_pki), key_cn, expiry, rotation_overlap, signing_key_file

5. Authentication

Login requires username + password + a TOTP code and returns a short-lived JWT plus a refresh token. Sessions are tracked and individually revocable.

When to use it

Every human caller authenticates here. Machine callers use service accounts (§9) instead.

Operations

POST /api/v1/users/login Authenticate, get a JWT
curl -s -X POST $BASE/api/v1/users/login -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123","totp_code":"123456"}'
rocketvault users login \
  --username admin --password admin123 --totp-code 123456
{
  "token": "<redacted-jwt>",
  "refresh_token": "<redacted-jwt>",
  "user_id": "f99945c6-ded6-4d6d-96be-7a10a1fbe6fe",
  "username": "admin",
  "role": "admin"
}
Errors
401 bad credentials or TOTP · 429 rate-limited (5/min)
POST /api/v1/users/refresh Exchange a refresh token
curl -s -X POST $BASE/api/v1/users/refresh -H "Content-Type: application/json" \
  -d '{"refresh_token":"<rt>"}'
{ "token": "<redacted-jwt>", "refresh_token": "<redacted-jwt>" }
GET /api/v1/users/sessions JWT List active sessions
curl -s $BASE/api/v1/users/sessions -H "Authorization: Bearer $TOKEN"
DELETE /api/v1/users/sessions/{id} JWT Revoke one (or all with no id)
# one session
curl -s -X DELETE $BASE/api/v1/users/sessions/<id> -H "Authorization: Bearer $TOKEN"
# all sessions for the caller
curl -s -X DELETE $BASE/api/v1/users/sessions -H "Authorization: Bearer $TOKEN"
Auth endpoints are rate-limited (default 5 req/min) — see §21.

6. JWT Signing & Key Sources

What it is

JWTs are signed asymmetrically and verifiable via JWKS at /jwks.json. Three providers control where the signing key lives, set by jwt.key_source.

ProviderStorageAlgorithmRotation
os_store (default)OS keychain, PEM-file fallbackRS256No
self_pkiRocketVault's own encrypted DBES256Yes (runtime)
external_pkiPEM from file or env varRS256/ES256No

Operations

GET /jwks.json none Public JWK set
curl -s $BASE/jwks.json | jq '.keys[0].alg'
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "9d1c755f04ddbcfc",
      "n": "<base64url-modulus>",
      "e": "AQAB"
    }
  ]
}
POST /api/v1/jwks/rotate JWT · admin Rotate (self_pki only)
curl -s -X POST $BASE/api/v1/jwks/rotate -H "Authorization: Bearer $TOKEN"
With os_store the key lives in the OS keychain and rotation returns 400 — only self_pki supports runtime rotation. Headless hosts fall back to ~/.local/share/rocketvault/jwt-signing.pem (mode 0600).

7. User Management

Admins create, list, update, and delete users. Each user has a role (admin, user, or a scoped manager role) and a TOTP secret issued at creation.

When to use it

Onboard human operators. For automation, prefer a service account (§9).

Operations

POST /api/v1/users JWT · admin Create a user
curl -s -X POST $BASE/api/v1/users -H "Authorization: Bearer $TOKEN" \
  -d '{"username":"alice","password":"alicepassword123","role":"user"}'
rocketvault users create --username alice --role user \
  --username admin --password admin123 --totp-code 123456
{
  "id": "<uuid>",
  "username": "alice",
  "role": "user",
  "totp_secret": "<base32-secret>"
}
Errors
400 invalid role (one of secrets_manager, crypto_manager, certificate_manager, admin, user) · 401/403 non-admin caller
GET /api/v1/users JWT · admin List users
curl -s $BASE/api/v1/users -H "Authorization: Bearer $TOKEN"
PUT /api/v1/users/{id} JWT · admin Update a user
curl -s -X PUT $BASE/api/v1/users/<id> -H "Authorization: Bearer $TOKEN" \
  -d '{"role":"admin"}'
DELETE /api/v1/users/{id} JWT · admin Delete a user
curl -s -X DELETE $BASE/api/v1/users/<id> -H "Authorization: Bearer $TOKEN"

See also: Endpoint table — Manual Testing §7

8. RBAC & Access Policies

What it is

Two complementary controls: roles (admin vs user) gate broad operations, and access policies grant a specific principal (user or service account) access to a specific resource — a resource type/id plus allowed actions.

Operations

POST /api/v1/access-policies JWT Create a policy
curl -s -X POST $BASE/api/v1/access-policies -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"read-db-secret","principal_id":"<id>","resource_type":"secret","resource_id":"<id>","actions":["read"]}'
GET /api/v1/access-policies JWT List all
curl -s $BASE/api/v1/access-policies -H "Authorization: Bearer $TOKEN"
GET /api/v1/access-policies/{id} JWT Get one
curl -s $BASE/api/v1/access-policies/<id> -H "Authorization: Bearer $TOKEN"
PUT /api/v1/access-policies/{id} JWT Update
curl -s -X PUT $BASE/api/v1/access-policies/<id> -H "Authorization: Bearer $TOKEN" -d '{"actions":["read","update"]}'
DELETE /api/v1/access-policies/{id} JWT Delete
curl -s -X DELETE $BASE/api/v1/access-policies/<id> -H "Authorization: Bearer $TOKEN"
GET /api/v1/access-policies/principal/{id} JWT List by principal
curl -s $BASE/api/v1/access-policies/principal/<id> -H "Authorization: Bearer $TOKEN"

9. OAuth2 Service Accounts

A service account is a machine identity (Azure KV service-principal equivalent) that authenticates via the OAuth2 client-credentials flow — no TOTP. Service accounts are read-only consumers: they retrieve secrets/keys/certs an admin granted them.

When to use it

CI/CD pipelines, apps fetching config at runtime, service-to-service secrets, scheduled jobs.

Operations

POST /api/v1/service-accounts JWT · admin Create (secret shown once)
curl -s -X POST $BASE/api/v1/service-accounts -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"ci-pipeline","description":"CI/CD"}'
{
  "id": "<uuid>",
  "name": "ci-pipeline",
  "client_secret": "<shown-once-redacted>"
}
POST /api/v1/oauth2/token Basic Client-credentials token
curl -s -X POST $BASE/api/v1/oauth2/token \
  -u "ci-pipeline:$SECRET" -d "grant_type=client_credentials"
{ "access_token": "<redacted-jwt>", "token_type": "Bearer", "expires_in": 3600 }
POST /api/v1/service-accounts/{id}/rotate JWT · admin Rotate the secret
curl -s -X POST $BASE/api/v1/service-accounts/<id>/rotate -H "Authorization: Bearer $TOKEN"
DELETE /api/v1/service-accounts/{id} JWT · admin Delete (invalidates tokens)
curl -s -X DELETE $BASE/api/v1/service-accounts/<id> -H "Authorization: Bearer $TOKEN"
The client_id is the service-account name, not its UUID. Delete or rotate immediately invalidates live tokens.

See also: Consuming Secrets Guide, Endpoint table — Manual Testing §14

10. Secrets

What it is

Encrypted-at-rest key/value secrets (AES-256-GCM). Only the owner or an admin can read a secret via the flat routes. Secrets support tags, generation, and import/export.

When to use it

Store application credentials, API keys, connection strings — anything an app needs at runtime but must not hold in plaintext.

Operations

POST /api/v1/secrets JWT Create a secret
curl -s -X POST $BASE/api/v1/secrets -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"db-password","value":"s3cret","tags":["database"]}'
{
  "id": "<uuid>",
  "name": "db-password",
  "tags": ["database"],
  "version": 1,
  "enabled": true,
  "created_at": "2026-06-03T07:44:46Z"
}
Notes
The plaintext value is not returned on create; read it back with GET. Updating the value creates a new version (§11).
GET /api/v1/secrets/{id} JWT Get a secret (decrypted)
curl -s $BASE/api/v1/secrets/<id> -H "Authorization: Bearer $TOKEN"
{
  "id": "<uuid>",
  "name": "db-password",
  "value": "<decrypted-value>",
  "tags": ["database"],
  "version": 1,
  "enabled": true,
  "created_at": "2026-06-03T07:44:46Z"
}
GET /api/v1/secrets JWT List secrets
curl -s $BASE/api/v1/secrets -H "Authorization: Bearer $TOKEN"
PUT /api/v1/secrets/{id} JWT Update (new version)
curl -s -X PUT $BASE/api/v1/secrets/<id> -H "Authorization: Bearer $TOKEN" \
  -d '{"value":"newpass","tags":["database"]}'
DELETE /api/v1/secrets/{id} JWT Soft-delete
curl -s -X DELETE $BASE/api/v1/secrets/<id> -H "Authorization: Bearer $TOKEN"
POST /api/v1/secrets/generate JWT Generate a random value
curl -s -X POST $BASE/api/v1/secrets/generate -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"api-key","length":32,"type":"alphanumeric"}'
POST /api/v1/secrets/export JWT Export
curl -s -X POST $BASE/api/v1/secrets/export -H "Authorization: Bearer $TOKEN" -d '{"format":"json"}'
POST /api/v1/secrets/import JWT Import
curl -s -X POST $BASE/api/v1/secrets/import -H "Authorization: Bearer $TOKEN" \
  -d '{"secrets":[{"name":"imported","value":"v","tags":["x"]}]}'

12. Secret Rotation

What it is

Rotation policies define how often a secret should rotate, with reminder windows and optional auto-rotate. History is tracked, and due rotations can be queried. Managed primarily through the CLI.

Admin operations

Manage policies
rocketvault secrets rotation create --secret-id <id> --interval 30d \
  --username admin --password admin123 --totp-code 123456
rocketvault secrets rotation list   --username admin --password admin123 --totp-code 123456
Operate
rocketvault secrets rotation rotate  --secret-id <id> ...
rocketvault secrets rotation history --secret-id <id> ...
rocketvault secrets rotation status  ...

See also: Integration Examples — rotation

13. Keys

What it is

RSA and ECDSA private keys, encrypted at rest, with cryptographic operations (wrap/unwrap, sign/verify, encrypt/decrypt), rotation, and version history.

When to use it

Hold signing or encryption keys server-side so private material never leaves the vault.

Operations

POST /api/v1/keys JWT Create a key
# RSA: bits = 2048 | 3072 | 4096
curl -s -X POST $BASE/api/v1/keys -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"my-rsa-key","type":"RSA","bits":2048}'
# ECDSA: curve = P-256 | P-384 | P-521
curl -s -X POST $BASE/api/v1/keys -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"my-ec-key","type":"ECDSA","curve":"P-256"}'
{
  "id": "<uuid>",
  "name": "my-rsa-key",
  "type": "RSA",
  "bits": 2048,
  "enabled": true,
  "revoked": false,
  "tags": [],
  "user_id": "<uuid>",
  "created_at": "2026-06-03T07:44:46Z"
}
Notes
Use bits for RSA and curve for ECDSA. Private key material is never returned; a GET includes only public components (RSA n/e).
POST /api/v1/keys/{id}/rotate JWT Rotate
curl -s -X POST $BASE/api/v1/keys/<id>/rotate -H "Authorization: Bearer $TOKEN"
POST /api/v1/keys/{id}/sign JWT Sign
curl -s -X POST $BASE/api/v1/keys/<id>/sign -H "Authorization: Bearer $TOKEN" \
  -d '{"value":"aGVsbG8=","algorithm":"RS256"}'
POST /api/v1/keys/{id}/verify JWT Verify
curl -s -X POST $BASE/api/v1/keys/<id>/verify -H "Authorization: Bearer $TOKEN" \
  -d '{"value":"aGVsbG8=","signature":"<sig>","algorithm":"RS256"}'
POST /api/v1/keys/{id}/wrap JWT Wrap (encrypt)
curl -s -X POST $BASE/api/v1/keys/<id>/wrap -H "Authorization: Bearer $TOKEN" -d '{"plaintext":"..."}'
POST /api/v1/keys/{id}/unwrap JWT Unwrap (decrypt)
curl -s -X POST $BASE/api/v1/keys/<id>/unwrap -H "Authorization: Bearer $TOKEN" -d '{"ciphertext":"<ct>"}'
POST /api/v1/keys/{id}/encrypt JWT Encrypt
curl -s -X POST $BASE/api/v1/keys/<id>/encrypt -H "Authorization: Bearer $TOKEN" -d '{"value":"aGVsbG8=","algorithm":"RSA-OAEP"}'
POST /api/v1/keys/{id}/decrypt JWT Decrypt
curl -s -X POST $BASE/api/v1/keys/<id>/decrypt -H "Authorization: Bearer $TOKEN" -d '{"value":"<ct>","algorithm":"RSA-OAEP"}'
GET /api/v1/keys/{id}/versions JWT List key versions
curl -s $BASE/api/v1/keys/<id>/versions -H "Authorization: Bearer $TOKEN"
DELETE /api/v1/keys/{id} JWT Soft-delete
curl -s -X DELETE $BASE/api/v1/keys/<id> -H "Authorization: Bearer $TOKEN"

GET /api/v1/certificates/{id} JWT Get
curl -s $BASE/api/v1/certificates/<id> -H "Authorization: Bearer $TOKEN"
PUT /api/v1/certificates/{id} JWT Update
curl -s -X PUT $BASE/api/v1/certificates/<id> -H "Authorization: Bearer $TOKEN" -d '{"name":"renamed"}'
DELETE /api/v1/certificates/{id} JWT Soft-delete
curl -s -X DELETE $BASE/api/v1/certificates/<id> -H "Authorization: Bearer $TOKEN"
GET /api/v1/certificates/{id}/policy JWT Get policy
curl -s $BASE/api/v1/certificates/<id>/policy -H "Authorization: Bearer $TOKEN"
PUT /api/v1/certificates/{id}/policy JWT Upsert policy
curl -s -X PUT $BASE/api/v1/certificates/<id>/policy -H "Authorization: Bearer $TOKEN" \

15. Multi-Vault

What it is

Resources live in named vaults (Azure KV parity). A built-in default vault holds everything created via the flat routes. Vault names are 3–63 lowercase alphanumerics/hyphens, no leading/trailing hyphen.

Visibility model

Route familyExampleVisibility
FlatGET /api/v1/secretsPer-user (owner only)
Vault-scopedGET /api/v1/vaults/{name}/secretsMembers see all

Operations

POST /api/v1/vaults JWT · admin Create a vault
curl -s -X POST $BASE/api/v1/vaults -H "Authorization: Bearer $TOKEN" -d '{"name":"team-alpha"}'
{
  "id": "<uuid>",
  "name": "team-alpha",
  "enabled": true,
  "purge_protection": false,
  "retention_days": 90,
  "created_by": "<uuid>",
  "created_at": "2026-06-03T07:44:46Z"
}
GET /api/v1/vaults JWT · admin List (?include_deleted=true)
curl -s "$BASE/api/v1/vaults?include_deleted=true" -H "Authorization: Bearer $TOKEN"
PATCH /api/v1/vaults/{name} JWT · admin Update
curl -s -X PATCH $BASE/api/v1/vaults/team-alpha -H "Authorization: Bearer $TOKEN" -d '{"retention_days":7}'
DELETE /api/v1/vaults/{name} JWT · admin Soft-delete (204; refuses default)
curl -s -i -X DELETE $BASE/api/v1/vaults/team-alpha -H "Authorization: Bearer $TOKEN"
rocketvault vaults create|recover|purge team-alpha ...
Vault management requires the vaults:manage permission (admin only). The default vault cannot be deleted.

16. Soft-Delete, Restore & Purge

What it is

Secrets, keys, and certificates are soft-deleted (retained, default 30 days) and can be restored or permanently purged. Purge protection can block permanent deletion.

Operations

GET /api/v1/deleted/secrets JWT List soft-deleted (flat, per-user)
curl -s $BASE/api/v1/deleted/secrets -H "Authorization: Bearer $TOKEN"
POST /api/v1/deleted/secrets/{id}/restore JWT Restore
curl -s -X POST $BASE/api/v1/deleted/secrets/<id>/restore -H "Authorization: Bearer $TOKEN"
DELETE /api/v1/deleted/secrets/{id}/purge JWT Purge permanently
curl -s -X DELETE $BASE/api/v1/deleted/secrets/<id>/purge -H "Authorization: Bearer $TOKEN"
GET /api/v1/vaults/{name}/deleted/secrets JWT Vault-scoped list (by membership)
curl -s $BASE/api/v1/vaults/default/deleted/secrets -H "Authorization: Bearer $TOKEN"
Key and certificate restore/purge are exposed only on the flat /deleted/keys/… and /deleted/certificates/… routes.

17. Audit Logs & Compliance

What it is

Every security-relevant action is recorded in a hash-chained audit log (tamper-evident). Logs are queryable with filters, and SOC 2 / GDPR reports can be generated. Admin only.

Operations

GET /api/v1/audit/logs JWT · admin Query logs
curl -s "$BASE/api/v1/audit/logs?action=login&limit=50" -H "Authorization: Bearer $TOKEN"
{
  "logs": [ /* ... */ ],
  "total": 42,
  "integrity_ok": true,
  "next_cursor": ""
}
GET /api/v1/audit/reports/soc2 JWT · admin SOC 2 report
curl -s "$BASE/api/v1/audit/reports/soc2?start_date=2026-01-01&end_date=2026-06-01" -H "Authorization: Bearer $TOKEN"
GET /api/v1/audit/reports/gdpr JWT · admin GDPR data-subject export
curl -s "$BASE/api/v1/audit/reports/gdpr?subject_id=<id>" -H "Authorization: Bearer $TOKEN"
GET /api/v1/audit/config JWT · admin Get retention config
curl -s $BASE/api/v1/audit/config -H "Authorization: Bearer $TOKEN"
PATCH /api/v1/audit/config JWT · admin Update retention
curl -s -X PATCH $BASE/api/v1/audit/config -H "Authorization: Bearer $TOKEN" -d '{"retention_days":365}'
The logs response carries an integrity_ok flag — the result of verifying the hash chain.

See also: Manual Testing

18. Backup & Restore

What it is

Two levels: full database backups via the CLI, and per-item encrypted backup/restore blobs for individual secrets, keys, and certificates via the API.

Full backup (CLI)

rocketvault backup create  --username admin --password admin123 --totp-code 123456
rocketvault backup list    --username admin --password admin123 --totp-code 123456
rocketvault backup restore --file /path/backup.json ...

Per-item (API)

POST /api/v1/secrets/{id}/backup JWT Back up one item
curl -s -X POST $BASE/api/v1/secrets/<id>/backup -H "Authorization: Bearer $TOKEN"
POST /api/v1/secrets/restore JWT Restore from a blob
curl -s -X POST $BASE/api/v1/secrets/restore -H "Authorization: Bearer $TOKEN" -d '{...blob...}'
Keys and certificates have the same per-item routes: /keys/{id}/backup, /keys/restore, /certificates/{id}/backup, /certificates/restore.

See also: Integration Examples — backup

19. HSM / PKCS#11

What it is

RocketVault can store and operate keys on a PKCS#11 token (hardware HSM, or SoftHSM2 for testing). Enable via the hsm config block; keys are stored as pkcs11:<uuid> instead of an encrypted PEM blob.

Configuration

hsm:
  enabled: true
  lib_path: /usr/lib/softhsm/libsofthsm2.so
  token_label: rocketvault
  pin: "1234"
  slot_id: 0

Supported algorithms

OperationAlgorithms
Sign / VerifyRS256/384/512, PS256/384/512, ES256/384/512
Encrypt / DecryptRSA-OAEP (SHA-1), RSA-OAEP-256 (SHA-256)
Key generationRSA 2048/4096, ECDSA P-256/384/521
Look for PKCS#11 HSM key provider initialised in the logs. P-256K (secp256k1) always uses the software provider.

21. Rate Limiting

What it is

Per-IP rate limits protect the API. Auth endpoints have a tighter limit than general endpoints.

Endpoint groupDefault (dev)
All API endpoints300 req/min
Auth (/login, /refresh, /oauth2/token)5 req/min
Tune via the rate_limit.default and rate_limit.auth config keys. Exceeding a limit returns 429 Too Many Requests.

22. Performance Internals

What it is

Two tunable subsystems run transparently. Caching: an in-memory key cache (key_cache.*, default 60s TTL / 500 entries) and a secret cache speed up reads. Retry: database and external-service operations use exponential backoff with jitter and a circuit breaker (retry.*).

These are configuration-tuned rather than operated directly — defaults are production-safe. Adjust only with measurement. The key_cache and retry blocks in §4 Configuration list the tunable keys.

See also: System Architecture (caching, retry, and circuit-breaker internals are shown in the service-layer diagram)

25. Consuming Secrets in Your Application

What it is

Applications retrieve secrets at runtime using a service-account OAuth2 token, so secrets never live in code or config. Three integration styles are supported.

Options

Go (vaultclient)
client, _ := vaultclient.New(vaultclient.Config{
  URL:          "http://localhost:8774",
  ClientID:     "my-app",                 // SA name
  ClientSecret: os.Getenv("VAULT_CLIENT_SECRET"),
  Secrets: []vaultclient.SecretMapping{
    {Name:"DB_PASSWORD", UUID:"<uuid>"}},
})
secrets, _ := client.GetMany(ctx, []string{"DB_PASSWORD"})
Shell / direct HTTP
# Get token
curl -X POST $BASE/api/v1/oauth2/token \
  -d "grant_type=client_credentials&client_id=my-app&client_secret=$SEC"
# Fetch a secret by UUID
curl $BASE/api/v1/secrets/<uuid> -H "Authorization: Bearer <access_token>"
VAULT_CLIENT_SECRET must come from an environment variable, never a config file. The server's own vault_client.client_id must be empty.

See also: Consuming Secrets Guide

Appendix D — Security Checklist

  • VAULT_CLIENT_SECRET in env vars only — never a config file or git.
  • Server's vault_client.client_id is empty (the server must not call itself).
  • Each application has its own least-privilege service account.
  • Rotate service-account secrets periodically (/service-accounts/{id}/rotate).
  • JWT signing key persists across restarts (keychain or 0600 PEM) — never in /etc/ssl/certs.
  • Audit retention configured; verify integrity_ok on audit queries.
  • Purge protection enabled for sensitive vaults.
